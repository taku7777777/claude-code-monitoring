# 運用ランブック — どの view を・どの順で・何を見るか

各ダッシュボードは役割が違う。**時間レンジの規律**を守ることが最重要:

| ダッシュボード | 役割 | 見るレンジ | 頻度 |
|---|---|---|---|
| **Today** | 今の使用状況の常時把握・ガードレール（Inform/Guard） | now/d（当日・30秒更新） | 日中に随時5秒 |
| **Usage** | 日々の消費の体感把握（Inform） | 24h（既定） | 毎日 2分 |
| **Cost Optimization** | 意思決定・効果検証（Optimize/Operate） | **7d（既定）** | 週1回 15分 |
| **Context** | 異常の深掘り（診断） | 3h〜当日 | スパイク時のみ |

30分レンジで日次系パネル（日次コスト推移・管理図）が No data になるのは仕様。
月次着地予測も短レンジでは外挿が暴れるため **7d で見た値だけを信じる**。

---

## 1. 毎日のクイックチェック（Today → Usage・2分）

まず **Today**（now/d・30秒更新）のガードレール stat を3秒眺める。現行の判定は
**背景比率**（repl_main_thread・agent:* 以外 ÷ 全体。≥20%黄 / ≥35%赤 / 本日 $5未満はグレー）と
**キャッシュ有効率**（cache_read/(cache_read+cache_creation+input)。<85%黄 / <70%赤 / 分母100万未満グレー）。
ラベル漏れ（unlabeled / `(unset)`）と auto-compact は **workspace別サマリ**の行・列で拾う。
黄・赤が無ければ深掘りしない（**グレー「分母不足」は正常**＝判定保留）。

続いて **Usage**（24h）上段の Stat 行を左から右に流す。「変だったら止まる」ためのビュー。

1. **コスト / ($/h)** — 昨日と同じ桁か。倍増していたら §3 の深掘りへ。
2. **ワークスペース別コスト推移** — 意図したプロジェクトに金が流れているか。
   `(unset)` が増え始めたら計測の退行（新プロジェクトに .claude/settings.json が無い、
   または起動経路の変化）。requirements 5.2.1 の 1↔2 を確認。
3. **モデル別コスト** — 高額モデルの比率は意図通りか。「うっかり Fable/Opus で
   雑タスク」を翌日に発見するのがこのパネルの仕事。
4. **ソース別コスト** — `repl_main_thread`（本作業）以外の背景コスト
   （`prompt_suggestion` / `away_summary` / `compact`）が肥大していないか。
   背景系が2割を超えたら削減候補（機能オフ・頻度調整が効く「タダで拾える」施策）。
5. **放置率 / 待機時間** — コストではなく自分の使い方の指標。放置率が高い日は
   「セッションを開きっぱなしで別作業」しており、context が無駄に伸びやすい。

## 2. 週次レビュー（Cost Optimization・7d・15分）— 意思決定の場

このダッシュボードは上から下へ「**単位コスト → 分布 → 予算 → 効果検証 → 犯人探し**」
の順に並べてあるので、そのまま上から読む。

### 2.1 概況（単位コスト）: 「効率」を先に見る
- **CPSO（成果あたりコスト）** が主指標。コストは仕事量で増減するので、
  コストだけ見て一喜一憂しない。CPSO が先週比 +30% を超えたら要因分析へ。
- **コスト/1M実効トークン** はモデル構成・キャッシュ効率の複合指標。
  CPSO が動いたとき「単価が動いた（→2.4へ）」のか「成果数が動いた」のかを切り分ける。
- **キャッシュ有効率**（cache_read/(cache_read+cache_creation+input)）は 85% 以上が健全圏。急落時は長時間セッションの
  開きっぱなし・頻繁な /clear・巨大 CLAUDE.md 変更を疑う。
- 前提: CPSO の分母は task_outcome。**Stop 到達の completed は弱いプロキシ**なので、
  重要タスクは `task-outcome.sh success|failure` で手動記録する習慣が分母の質を決める。

### 2.2 ベースライン（分布）: 「普通」を数字で持つ
- p50/p90/p95(期間) の3値を**自分の基準値**としてメモしておく（例: p50 $0.20 /
  p90 $0.39 / p95 $0.89）。以後の「高い/安い」はこの分布との比較で言う。平均は使わない。
- 単位コスト分布パネルで p95 を超える外れ値が**特定 workspace に偏る**なら、そのプロジェクトの
  CLAUDE.md / コンテキスト運用の問題。全体に散るなら使い方（モデル選択）の問題。

### 2.3 バーンレート / 予算
- 月次着地予測(USD) を予算と照合。7d ベースの外挿なので、先週施策を打った場合は
  今週の値が「施策後の着地」になっている点に注意。
- 日次コスト推移はデータが3日以上溜まってから意味を持つ。曜日パターン
  （平日高・週末低など）を掴むのが目的。

### 2.4 診断（寄与度・帰属）: 削減候補は必ずここから選ぶ
読み順は **prompt top15 → model → source → work_type**:
1. **コストドライバ prompt別 top15** — 上位2〜3件で全体の過半を占めるのが通常
   （パレート）。高額 prompt の id を控えて Context ダッシュボードで深掘り（§3）。
2. **model別コスト** — 高額モデル比率。「Fable/Opus は設計・レビューだけ、
   実装は Sonnet」のようなルールを作る根拠になる。
3. **query_source別コスト** — 背景コスト（prompt_suggestion 等）の絶対額。
   本作業の 2割を超えていたら設定で削る。
4. **実効トークン vs 生トークン** — 乖離が大きい＝キャッシュで守られている。
   2線が近づいてきたらキャッシュ効率の劣化サイン。

### 2.5 サブエージェント（委任率と適切さ）

計測の仕組み: サブエージェントの API 呼び出しは `query_source="agent:<種別>"` として
本体（`repl_main_thread`）と区別され、**親と同じ session_id / prompt_id を引き継ぐ**
（実測確認済み）。本体側の委任アクションは `tool_decision | tool_name="Agent"` で計数できる。

読み方（Cost Optimization「サブエージェント」セクション）:

- **委任率（コスト比）** — 絶対の正解値はないが、両極端が異常サイン:
  - **0% に張り付く週** × Context の取り込み/生成比 top10 が高い（15超）
    → 広域探索・大量ファイル読みを main context でやっている。委任すれば
    main の context 汚染（compaction・単価上昇）を防げる。委任の第一候補。
  - **高委任率なのに CPSO 悪化** → 過剰 fan-out（重複探索・要らない並列・
    「とりあえず agent」）。呼び出し回数と $/起動 の積で確認する。
- **$/起動（サブエージェント平均コスト）** — ベースライン化して監視。急騰の
  典型原因は「軽作業（検索・列挙）に重いモデル」か「agent プロンプトが重すぎて
  長時間走る」のどちらか。
- **agent種別 × モデル テーブル** — 適切さの主検査点。検索/探索系
  （Explore 等）が Fable/Opus で動いていたら過剰スペック（Haiku/Sonnet で足りる）。
  意図した使い分け（設計レビューは重いモデル、機械的作業は軽いモデル）に
  なっているかを週次で1回眺める。
- **本体 vs サブエージェント推移** — subagent_policy カテゴリの施策
  （「探索は必ず委任する」等）を打ったら、このパネル＋マーカーで構成変化を確認し、
  効果は CPSO / 管理図で判定する（§4）。

週次レビューの出口は「**今週打つ施策を1つ決める**」こと。候補は RICE で優先度付け
（`analysis/cost-optimization-analyzer.py` が支援）。同時に複数打つと効果検証が濁る。

## 3. スパイクの深掘り（Context・当日レンジ・随時）

Usage/CostOpt で「高い prompt / 高い日」を見つけたときだけ開く。

1. **prompt別cost top10** で該当 prompt を特定 →
2. **prompt別取り込み/生成比 top10** — 比が 15 超なら「読み込み過多」
   （巨大ファイル Read、無駄な再読、subagent なしの広域探索）。
   **prompt別turn数 top10** — turn 数過多なら「1プロンプトに詰め込みすぎ/手戻り」。
3. **セッション別context量推移** — 単調増加で 150K 超に張り付くセッションは
   開きっぱなし。/clear or 新セッションで単価が下がる。
4. **cacheRead比率 / compaction** — 比率の谷が頻発するなら不安定なプロンプト先頭
   （CLAUDE.md・system の変更）や長い放置を疑う。auto-compact が頻発する
   ワークフローは取り込み削減の施策対象。

## 4. 施策サイクル（Operate）— 感覚値で終わらせない手順

1. **打つ前にマーカー**: `scripts/intervention-marker.sh --category model_switch --desc "実装はSonnet既定に変更"`
   → 全ダッシュボードに縦線 annotation が入り、before/after の照合点になる。
2. **1〜2週間は他の施策を打たない**（交絡防止）。
3. **判定は2段**:
   - 目視: Cost Opt「効果検証」セクションで管理図（日次 コスト/1M実効トークン）の
     水準がマーカー後に下がったか。
   - 客観: `python3 analysis/cost-optimization-analyzer.py` の [f] が
     I-MR 管理限界（X̄±2.66·MR̄）でシフト有意性を判定。**有意でなければ
     「効果なし」と記録して戻す**。ここで感覚値を切る。
4. 結果（採用/棄却）をメモに残し、次の施策候補（§2.4）へ。

## 5. 月次（10分）

- `analysis/cost-optimization-analyzer.py --archive` をフル実行: CPSO 推移・パレート・
  CUSUM 変化点・モデル経済性（cost_usd と再計算の乖離、`--cf-target` 反実仮想、
  キャッシュ純節約$）・[h] タスク別サマリ（CPSO/委任率/探索コスト比/rework比率）を確認。
  `--archive` が analysis/archive/ に CSV を残すので、Loki retention（90日）を超える
  タスク長期比較はこの CSV で行う。
- **請求突合と単価是正（校正ループ / ADR 0006）**: console.anthropic.com の請求と
  ダッシュボードのコスト（cost_recalc）を突合。乖離があれば `pricing/pricing.yaml` を是正し、
  `python3 scripts/gen-cost-recalc.py && docker compose restart otel-collector` で
  collector の計算式を再生成（生成漏れは `--check` で検知）。変更したら
  `intervention-marker.sh --category other --desc "pricing更新"` を打つ。
  概況の「SDK推定との乖離」が±数%を超えて定着した場合も同じ手順
  （SDK 側が先に価格改定に追随したサイン）。
- Loki retention（90日）を超える前に、残したい月次サマリは analyzer --archive の CSV で永続化する。

## 既知の読み方の注意

- **completed は弱いプロキシ**: 直近の task_outcome テーブルが completed だらけなのは
  正常（Stop 到達ごとに自動記録）。CPSO を厳密にしたい期間は手動記録を併用する。
- **現在の最大context量の赤閾値**は 200K コンテキスト前提。1M コンテキストモデル
  （fable/opus[1m]）では 188K でも 19% 消費に過ぎない。
- **コスト表示は cost_recalc（単価表×実トークンの再計算値 / ADR 0006）**: pricing.yaml を
  請求と突合して是正すれば表示が実態に収束する。SDK 推定（cost_usd）はイベントに併存し、
  概況の乖離 stat と analyzer [g] で突合する。ground truth はあくまで請求（§5）。
  切替日（2026-07-12）以前のデータは cost_usd で表示される（クエリ側 coalesce。
  差は±数%で、90日後に全量が cost_recalc になる）。
