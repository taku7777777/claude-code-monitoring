# 概況（単位コスト）

「いくら使った → 何回分の仕事か → 効率は → 単価構成は → キャッシュは効いてるか → 計測は信頼できるか」の並び。

## 1. コスト

### 表示
- 指定期間内に実際に発生しているコストの概算
- 表示期間内の api_request cost_recalc（単価表×実トークンの再計算値 —
  定義は [CONTRACT §3.1](../../CONTRACT.md)、経緯は
  [ADR 0006](../../adr/0006-cost-recalc-in-collector.md)）の合計
- 公式請求ではないが、単価表を実請求との突合で是正すれば実態に収束させられる
  （是正は将来分に反映。手順は RUNBOOK §5）
- SDK推定（cost_usd）とは別系統。両者のズレは「6. SDK推定との乖離」で監視する
- 切替日（2026-07-12）以前のイベントは cost_recalc を持たないため cost_usd で表示される
  （クエリ側 coalesce — [ADR 0006](../../adr/0006-cost-recalc-in-collector.md)）

### 活用
- 予算・許容範囲との照合のみを行う
- ROI(コスト対効果)や効率が高いかの判断はしない(仕事量に比例して増えるのが当然なので)
- ROIや効率は CPSO など他の項目をもとに判断する

## 2. プロンプト完遂数

### 表示
- 指定期間内に完遂（応答完了 = Stop まで完走）したプロンプトの数
- 仕事量をカウントするためのもので、成果の代理値として扱うためのもの
- 完遂は「Stop に到達した」ことを指し、内容の品質や成功を保証するものではない
- `task_outcome` イベント（詳細は
  [CONTRACT §3.2](../../CONTRACT.md)）の、成功系（`outcome` が failure / abandoned 以外）の
  件数から失敗系の件数を引いた値（減算方式）。発生源は以下のいずれか
  1. 応答完了（Stop）ごとの自動 completed
  2. `task-outcome.sh` の手動記録
- 完遂（Stop 到達）に至らなかった送信 — 追い打ちによる打ち切り・中断・
  ローカルコマンド等 — は計上されない
- 人手を介さない自動起動セッション（cmux 等）の completed も計上される（除外されない）
- 手動記録 `task-outcome.sh failure`（失敗）/ `abandoned`（中断・放棄）は**減算**として
  効き、並存する自動 completed を相殺する（CONTRACT §3.2）
- Stop 未到達のタスクに failure/abandoned を記録した場合は相殺相手が無く、
  1件分の過剰減算（保守側の誤差）になる
- 手動 success は自動 completed と重複し、同一タスクが2件計上されうる
  （分離不可 — CONTRACT §3.2）
- 手動記録はプロンプト単位でなくタスク単位の記録のため、厳密にはプロンプト以外の
  完遂も少数含みうる

### 活用
- 実行数ごとのコストが妥当かの判断を実現するための `CPSO` の分母（仕事量）として使う
- タスク単位の成果管理はしない（タスクの経済性は workspace ごとの合算で判断する）
- 自動起動セッションの completed が混ざると本指標が水増しされ CPSO が実態より低く出る。
  区別は起動ディレクトリに自動起動用の work_type `auto` を設定して行う（CONTRACT §5.5）

## 3. 成果あたりコスト(CPSO)

### 表示
- プロンプト完遂1回あたりの平均コスト（CPSO = Cost Per Successful Outcome）
- コスト ÷ プロンプト完遂数
- 平均のため外れ値1件で大きく動く（例: 完遂50件の期間なら $20 のプロンプト1件で
  約 $0.4 上がる）

### 活用
- 効率の主指標。効率の良し悪しはこのパネルを起点に判断する
- コスト増＋CPSO横ばい＝仕事量が増えただけ（健全）。
  CPSO上昇＝同じ仕事に多く払っている（劣化）
- 前週比 +30% を超えたら診断セクションで要因分析する
- 外れ値・ブレの議論はここではしない（分布はベースラインセクションで見る）

## 4. コスト/1M実効トークン

### 表示
- 実効トークン100万個あたりの支払額。モデルミックスの体温計
- $ ÷（実効トークン/1,000,000）。実効トークン =
  input×1.0 + cache_read×0.1 + cache_creation×1.25 + output×5.0
  （価格表の単価比で重み付け。ただし cache_creation の 1.25 のみ 5分TTL 基準の
  据え置き規約値。定義の正本は [CONTRACT §5](../../CONTRACT.md)）
- 実効トークンは入力単価比の重み付けなので、この値は「使ったモデルミックスの実効入力単価
  ($/MTok)」にほぼ一致し、pricing.yaml の単価（2026-07 時点: fable=10 / opus=5 /
  sonnet=3 / haiku=1.5）と同じ目盛りで読める
- 重みが価格比のため、モデル構成が同じならほぼ一定になる設計
- cache_creation の重み 1.25 は 5分TTL 基準の据え置き規約値（実課金仮定は 1h = 2.0x）。
  金額の正確性は cost_recalc が担う（CONTRACT §5）

### 活用
- 上昇＝高額モデル比率の増加のサイン。小さい方が良いが、本質は「安定しているか」
- CPSO とペアで読む。逆方向に動いたら「安いモデル×ラリー増で逆に高い」等の
  トレードオフ発生サイン
- 成果定義に依存しないため、施策の効果検証はこの指標で行う（効果検証セクション）

## 5. キャッシュ有効率

### 表示
- プロンプト側トークンのうち 1/10 価格のキャッシュで処理できた割合
- cache_read ÷（cache_read + cache_creation + input）。
  Usage「1. キャッシュ有効率」（[usage/01-health.md](../usage/01-health.md)）と同一式
  （ただし本パネルは workspace 変数で絞り込む。Usage 側は全 workspace 固定）

### 活用
- 「無駄な再課金が起きていないか」の検知。85%以上が健全圏
- 下がる要因: 新セッション・/clear直後・CLAUDE.md等の変更直後・
  キャッシュTTL超えの放置後再開・セッション乱発
- 率が高くても安心しない: 巨大 context を引きずっても率は高く出る
  （1/10価格でも量が膨大なら$は嵩む）
- 率＝無駄の検知、量＝実効トークン、と役割分担して読む

## 6. SDK推定との乖離

### 表示
- 自前再計算（cost_recalc）と SDK 推定（cost_usd）のズレの割合
- 単価表（pricing.yaml）が実勢からズレていないかを検知するための計測系ヘルスチェック
- (cost_usd 合計 − cost_recalc 合計) ÷ cost_recalc 合計。
  単価表で計算できたイベント（cost_recalc_src="pricing"）のみで比較する
- 未定義モデルのイベント（cost_usd へのフォールバック）は比較に含まれない。
  そのため fallback の混入自体はこのパネルでは検知できない（pricing.yaml 未定義モデルの
  発生は analyzer（analysis/cost-optimization-analyzer.py）の [g] が警告する）
- workspace 変数では絞り込まない（全 workspace 対象の計測系チェック）

### 活用
- ±数%が正常圏（2026-07-12 校正時点で +3.9%/24h）。黄 ±10% / 赤 ±25%
- 負側への定常的な振れはキャッシュ書込 TTL 仮定（1h=2.0x）の過大サイン（ADR 0006）
- 定常的に超えたら単価ズレ（価格改定・新モデル・キャッシュTTL仮定）を疑い、
  公式 pricing・実請求と突合 → pricing.yaml 是正 → `scripts/gen-cost-recalc.py` 再生成 →
  collector 再起動（RUNBOOK §5）
- コスト効率や使い方の判断はしない（計測の健全性チェック専用）
