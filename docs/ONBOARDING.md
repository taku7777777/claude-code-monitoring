# オンボーディング — 触って覚えるダッシュボードの読み方

このリポジトリのダッシュボードを **「自分で操作して、その結果が画面にどう出るか」を試しながら** 覚えるためのハンズオン。
「どんなプロンプトや処理が、ダッシュ上でどう表現されるか」を体感して、値を読む勘を作るのが目的。

- **なぜ見るのか（ユースケース）** → [USECASE.md](USECASE.md)
- **実測値でどう診断するか（熟練者の型）** → [CASEBOOK.md](CASEBOOK.md)
- **各値の厳密な定義** → [CONTRACT.md](CONTRACT.md) / [docs/3-requirements/](3-requirements/)
- **本書** = その手前。「操作 → 画面の変化」を1対1で体験する実験ノート。

## 0. 準備 — 自分の活動を計測に乗せる

```bash
scripts/stack-up.sh          # Loki + Prometheus + Grafana + otel-collector を起動
open http://localhost:3033   # Grafana（匿名Viewerで閲覧可 / 編集は admin/admin）
```

**タスクは必ずタスク用ディレクトリから起動する**（= タスク = workspace 運用）:

```bash
scripts/init-task-workspace.sh ~/github/task-20260715-onboarding --type chore
# 生成された dir で claude を起動すると workspace ラベルが付く
```

> ⚠️ workspace を設定せずに作業すると `unlabeled`（または親dirの名前）に化けて帰属不能になる。
> これ自体が実験 **E7** の題材。

計測が乗っているかは **Today** の「本日コスト」が数十秒〜数分で増えることで確認できる（イベントは otel-collector 経由で準リアルタイムに Loki へ入る）。

### 5分スモークテスト（パイプライン疎通の自己確認）

初回はまずここで「自分の操作がちゃんと計測に乗る」ことを確かめる。

```bash
docker ps                                              # loki / prometheus / grafana / otel-collector が Up か
curl -s http://127.0.0.1:3100/loki/api/v1/labels       # event_name / workspace 等が返れば Loki 生存
```

1. タスクdir で `claude` を起動し、最小プロンプト1本（例:「この README を一文で要約して」）を送る。
2. 30〜60秒後、**Prompt List**（または Today）に自分の1行が出れば取り込みOK。
3. **フック疎通**: 応答完了（Stop）後、Loki で `{event_name="task_outcome"}` が1件増えるか。
   > ⚠️ **jq が未導入だとフックは無音で欠落する**（エラーも出ない）。`jq` を入れておく。
4. **帰属確認**: Today の `workspace別サマリ` で、自分の作業が `unlabeled` / `(unset)` に落ちていないか（落ちていれば §0 の init を忘れている）。

## 1. 画面地図 — 2つの「考える画面」＋ドリルダウン階層

考える起点は2枚。他はそこから**絞り込んで降りる**ための詳細画面。

| 起点画面 | いつ見る | 主な問い |
|---|---|---|
| **Today** | 今まさに作業中 | 今どれだけ使った？ context は詰まってない？ 放置してない？ |
| **Cost Optimization** | 日次/週次の振り返り | 単価効率は？ 何が高い？ 施策は効いた？ |

**ドリルダウン階層（List → Detail）** — 画面上部の `Usage / Cost Optimization / Sessions / Prompts` ナビと、表の行/セルのリンクで移動する:

```
Today ──(workspace別サマリの行をクリック)──▶ Workspace（そのタスク単体）
  └─(Sessions ナビ)──▶ Session List（そのworkspaceのセッション一覧）
        └─(session_id 行をクリック)──▶ Session Detail（そのセッション単体のUsage）
              └─(Prompts ナビ)──▶ Prompt List（そのセッションのプロンプト全量・実コスト）
                    └─(prompt_id をクリック)──▶ Prompt明細（1プロンプトの内訳）
```

**フィルタは遷移で引き継がれる**（`workspace` / `session_id`）。ドリルダウンした先で意図しない絞り込みが残っている場合は、上部の変数を `All` / `.*` に戻す。No data のときはまずここを疑う。

## 2. メトリクス早見表 — 観点 / どこを見る / 目安

| 指標 | 画面 | 観点（何を表す） | 健全の目安 / 悪化サイン |
|---|---|---|---|
| **本日コスト / コスト** | Today, Cost Opt | いくら使ったか（cost_recalc 合計） | 予算枠との照合のみ。効率判断はしない |
| **キャッシュ有効率** | Today, Cost Opt | プロンプト側トークンのうち 1/10価格キャッシュで処理できた割合 = cache_read/(cache_read+cache_creation+input) | **85%以上が健全**。**<85%黄 / <70%赤**。低下＝新セッション/clear直後/放置後再開 |
| **背景比率** | Today | 自分の依頼でない背景機能（away_summary 等）のコスト割合 = repl_main_thread・agent:* 以外 ÷ 全体 | **<20%が健全**。**≥20%黄 / ≥35%赤**。高い＝背景機能が費用を食っている |
| **取り込み比** | Prompt List | 新規取り込み量 ÷ 出力量 = cache_creation/output。「読む量に対して成果が少ない」度合い | **<15が健全 / オレンジ≥15 / 赤≥30**。高い＝読み込み過多・非効率 |
| **コスト/1M実効** | Cost Opt, 各サマリ | 使ったモデルミックスの実効入力単価（$/MTok）。実効tok = input×1.0+cache_read×0.1+cache_creation×1.25+output×5.0 | **安定していること**が本質。上昇＝高額モデル比率増（fable=10>opus=5>sonnet=3>haiku=1.5） |
| **CPSO（成果あたりコスト）** | Cost Opt | コスト ÷ プロンプト完遂数。効率の主指標 | 横ばい＝健全。**前週比+30%超で診断**。上昇＝同じ仕事に多く払っている |
| **コンテキスト遷移** | Today, Context | セッションごとの context_tokens の時系列 | 150K破線接近＝要 /compact。段差下降＝compact済。**15分以上の空白＝TTL経過（1h超で失効）** |
| **Claude放置率 / 待機時間** | Usage | Claudeが応答待ちで放置された割合・時間 | 高い＝着手せず放置。TTL失効→再構築費の温床 |
| **SDK推定との乖離** | Cost Opt | 自前再計算 cost_recalc と SDK 推定 cost_usd のズレ（計測ヘルス） | **±10%黄 / ±25%赤**。恒常的超過＝単価表ズレ（要 pricing.yaml 校正） |
| **実行時間 / 継続時間** | Prompt List / Session List | プロンプト/セッションの実時間（終了−開始） | 長時間×高コストの発見に使う |

> 数値の厳密な式・注意点は各 [3-requirements](3-requirements/) を参照。ここは「読む勘」用の要約。
>
> **グレー「分母不足」は正常**。比率系（背景比率・キャッシュ有効率など）は最低分母ガード付きで、
> 本日消費が少ない/1日最初のプロンプト等では判定を保留してグレー表示になる（＝異常ではない）。

## 3. 実験レシピ集 — 操作すると画面がこう動く

各実験は **狙い / やること / 見る場所 / 期待される表現 / 学び** の順。タスクdir（§0）から `claude` を起動して試す。反映は数十秒〜数分。

> 💡 **訓練のコツ**: やる前に「コストは幾ら？ どの値が動く？」を**先に予想**して紙にメモ →
> 実測と突き合わせ → 差の理由を言語化する。この「予想→実測→差の説明」を繰り返すのが単価感覚（UC1）の作り方。

### E1. 単価感覚 — 軽い往復 vs 重い往復
- **やること**: 新セッションで「1+1は？」と聞く。別途、大きめのコードベースで長く会話したセッションでも1往復する。
- **見る**: Prompt List の各行の `コスト` / `実効tok`、Session Detail の `コスト`。
- **期待**: 軽い往復 ≈ $0.1未満。context満載セッションの1往復 ≈ $0.5〜1。同じ「1往復」でも桁が違う。
- **学び**: コストは文章の長さでなく **引きずっている context 量** で決まる。

### E2. 取り込み過多 — 大きなファイルを一気に読ませる ⭐
- **やること**: 新セッションで「`docs/` 配下を全部読んで要約して」のように大量 Read を促す。
- **見る**: **Prompt List の `取り込み比`**（赤くなる）、Today の `コンテキスト遷移`（急増）、`キャッシュ有効率`（一時低下）。
- **期待**: そのプロンプトの取り込み比が 15〜数百に跳ねる。context_tokens が階段状に急上昇。
- **学び**: 「まず全部読ませる」粗い初手は割高。**対象ファイルを列挙してから**着手 or Explore委任が効く。

### E3. context を育てて /compact する
- **やること**: 同一セッションで往復を重ね、context を 150K 付近まで育ててから `/compact`。
- **見る**: Today / Context の `コンテキスト遷移`。
- **期待**: 破線（150K/200K）に向かって漸増 → `/compact` 直後に **段差で下降**。
- **学び**: 破線接近×まだ続ける、なら早めに手動 /compact。段差＝圧縮が効いた印。

### E4. 放置して TTL を失効させる
- **やること**: 応答後、そのまま15分以上放置してから再開。
- **見る**: `コンテキスト遷移`（線が途切れる＝空白）、Usage の `Claude放置率`、再開直後の `キャッシュ有効率`。
- **期待**: 15分の空白ができ、1h超なら再開時に cache_creation が増えて有効率が一時低下。
- **学び**: 長い放置はキャッシュTTL失効で **再構築費** を払う。続けるなら放置しない、離れるならセッションを切る。

### E5. サブエージェントに委任する
- **やること**: 「Explore エージェントでリポジトリ構成を調べて」のように委任させる。
- **見る**: Today の `コスト構成（query_source別）`（`agent:*` が出る）、`コンテキスト遷移`（親セッションは抑制的）、コスト構成のモデル内訳。
- **期待**: query_source に agent系が現れ、親 context の急増を避けられる。委任モデルが高額（fable）だとコスト/1M実効が上振れ。
- **学び**: 広域探索は委任で親 context を守る。ただし **委任モデルの選択**（Sonnet/Haiku 既定）で単価が大きく変わる。

### E6. 小さな依頼を高頻度で送る
- **やること**: 短い依頼を連続で10回投げる。
- **見る**: Session List の `リクエスト数`、Cost Opt の `プロンプト完遂数` / `CPSO`。
- **期待**: リクエスト数・完遂数が増える。1件が軽ければ CPSO は下がる方向。
- **学び**: 完遂数は CPSO の分母（仕事量の代理）。「安いモデル×ラリー増で逆に総額は高い」パターンにも注意（コスト/1M実効とペアで読む）。

### E7. workspace を付けずに作業する（失敗を体験）
- **やること**: タスクdir でない場所（例: `~/github` 直下）で claude を起動して何か実行。
- **見る**: Today の `workspace別サマリ`。
- **期待**: `unlabeled`（または `github`）にコストが落ちる＝どのタスクか帰属できない。
- **学び**: だから §0 の `init-task-workspace.sh` が要る。ラベル漏れは「unlabeled」に集めて毎日見えるようにするのが設計。

### E8. 施策マーカーを打つ（効果検証の起点）
- **やること**: `scripts/intervention-marker.sh --category subagent_policy --desc "委任をSonnet既定に変更"`
- **見る**: 時系列パネル（コンテキスト遷移 / コスト推移）に紫の縦線。
- **期待**: マーカー縦線が入り、前後で水準変化を目視比較できる。
- **学び**: 施策は**1本ずつ**打ってマーカー → 1〜2週間後に前後比較（[CASEBOOK](CASEBOOK.md) Case3）。

### E9. task-outcome を記録する
- **やること**: タスク完了時に `scripts/task-outcome.sh`（成功/失敗/中断）。
- **見る**: Cost Opt の `プロンプト完遂数` / `CPSO`。
- **期待**: 成功で完遂数+1、failure/abandoned は減算として効く。
- **学び**: CPSO の分母は自動 completed + 手動記録。中断を記録しないと成果が水増しされる。

### E10. モデルを変えて単価を動かす
- **やること**: 委任や作業のモデルを fable → sonnet/haiku に変えて同種の作業をする。
- **見る**: Cost Opt の `コスト/1M実効`、`コスト構成`のモデル内訳。
- **期待**: コスト/1M実効が単価比（10→3→1.5）に沿って下がる。
- **学び**: この指標は成果定義に依存しないので **施策の効果検証** に使える。

## 4. 自己分析の型（CASEBOOK への橋渡し）

どのケースも同じ5手で閉じる（詳細な実例は [CASEBOOK.md](CASEBOOK.md)）:

1. **検知** — 健康診断・ペース比・top15・前週比のどれかが黄赤/外れ値
2. **ベースライン比較** — 「高い」は必ず自分の p50/p90/p95 か過去同曜日比で言う
3. **帰属** — workspace（タスク）→ モデル → ソース → prompt の順で犯人を絞る
4. **明細で因果** — Prompt明細 / `scripts/show-session.sh <session_id>` で「なぜ」まで降りる
5. **施策はマーカーを打って1本ずつ** — 効果検証はコスト/1M実効と analyzer、有意でなければ戻す

## 5. 困ったとき — No data / 値が合わない

| 症状 | 原因と対処 |
|---|---|
| パネルが軒並み **No data** | 上部の `workspace` / `session_id` に前画面の絞り込みが残存。`All` / `.*` に戻す。時間レンジも確認 |
| ブラウザで直したはずの挙動が古い | ダッシュボード定義がブラウザキャッシュに残る。**ハードリフレッシュ**（Cmd+Shift+R） |
| フックのイベント（task_outcome 等）が出ない | **jq 未導入で無音欠落**／`.claude/settings.json` のフックパス未置換／Claude Code の再起動忘れ |
| 自分の作業が `unlabeled`/`(unset)`/`github` に化ける | タスクdir 以外から起動した。`scripts/init-task-workspace.sh` で settings を生成し起動し直す |
| 30分レンジで日次パネルが No data | 日次集計パネルはレンジが短いと母数が無く No data になる（仕様）。レンジを広げる |
| コンテキスト遷移の線が右端で途切れる | 最終活動からの経過（15分以上イベント無し）。1h超なら TTL 失効 |
| Prompt List の合計が Session コストと合わない | 現行はプロンプト一覧を **api_request 集計**（実コスト）で出すため一致するはず。合わない場合は時間レンジがセッション全体を含んでいるか確認 |
| workspace = `All` で No data | workspace 変数は単一選択（multi無効）。`All` は allValue `.*` で全 workspace にマッチする設計 |
