# Today — 判断と操作のシナリオ（judge & change）

このページ（Today）の値を見て**何を判断し、どの操作に繋げるか**の全体像。
パネル要件（[01](01-headroom.md)〜[06](06-delegation-model.md)）が「値→判断」を定義するのに
対し、本ファイルは**操作側からの逆引き**（この操作はいつ・何を根拠に実行するか）を
一覧で持つ。検知対象の全量は異常カタログ（[../draft-today.md](../draft-today.md)
A1〜A12）、施策としての効果検証は Cost Opt（[効果検証](../cost-optimization/04-verification.md)）の管轄。

## シナリオの型

**値を見る → 判断する → 操作する → 効果の出方を確認する**

- その場で完結する操作（compact / clear / モデル切替等）はそのまま実行する
- 恒常的な変更（背景機能オフ・agent model 指定等）は**施策**として扱う:
  `intervention-marker.sh` を打ってから変更し、効果は週次レビューで判定する
  （1本ずつ — 同時に打つと何が効いたか分からなくなる）

## 委任の使い分け基準（観測値ベース — O4/O5/O6 の深掘り）

委任の損益構造: agent は**使い捨て context**。「タスクが読む量 ≫ 持ち帰る量」なら
委任が得（main を汚さない）、逆に小さい仕事は起動ごとの構築費（prefix +
使い捨て context の cache_creation）が支配して損。事前判断はパターンで行い、
事後の観測値で自分の閾値を較正する2段構え。

**パターン → 委任の推奨**:

| パターン | 委任 | 根拠（観測値で裏付く理由） |
|---|---|---|
| 広域探索・コード検索・大量ファイル読み | **推奨**（Explore 系 + 軽モデル指定） | main でやると取り込み比 >15・context +50K/依頼級の汚染。agent 側なら使い捨て |
| 独立レビュー・検証・セカンドオピニオン | 推奨（並列は目安3まで） | 独立視点が価値。**並列自体は正当** — 起動数/依頼 >5 は「控えろ」でなく「意図した並列か」の突合トリガー（意図内なら閉じる） |
| 定型の一括変換（多ファイル migration） | 推奨（worktree 分離） | 同種編集の反復は main の文脈を必要としない。**手順が完全に確定しているならスクリプト化（O15）がさらに安い** |
| Web・ドキュメント調査 | 推奨 | 読む量 ≫ 報告量の典型（実測: guide 調査1件 $0.22）。※指標はタスク種の分類器ではなく「main が汚れたか」の実害計測 — 目的が調査でも記録でも、汚れたなら委任すべきだったの結論は同じ |
| 設計対話・要件のすり合わせ | **非推奨**（main 直） | main の文脈自体が資産。委任は文脈を分断する |
| 小さな質問・1〜2ファイルの修正 | 非推奨（main 直） | 委任すると産出/構築比が低く出る（構築費が支配） |

**観測値 → アクションの早見**（閾値はすべて自己基準の初期案。実測で較正）:

| 観測値（家） | 目安 | 読みとアクション |
|---|---|---|
| main 取り込み比 / prompt（プロンプト一覧） | >15 | この種の依頼は次から委任（O4）。実行直後に学習 |
| context 増分 / 依頼（Today 05 推移の段差） | +50K 超 | 委任 or 対象限定（O4/O10） |
| 委任逃し率（Cost Opt 06-6・週） | 高止まり | 委任習慣の施策（「探索は必ず委任」）を打つ |
| 起動数 / 依頼（Cost Opt 06-7・週） | >5 | fan-out 過剰の疑い。意図した並列なら想定内で閉じる |
| $/起動（Today 06 / Cost Opt） | 平常比で急騰 | 軽作業に重モデル（O6 — モデル×経路の委任列で確認）か agent プロンプト過重 |
| 産出/構築比（Cost Opt 06-8・週） | 低下傾向 | 委任の粒度が細かすぎ → 依頼をまとめる・main 直に戻す |

## キャッシュ有効率の判断基準（高率 ≠ 善）

キャッシュの経済性は3軸で判断する。**有効率は「無駄な再課金の検知」専用**で、
高率のまま損をする形が2つある。

- **① 構成（率）**: キャッシュ有効率。低下 = どこかで prefix が途切れた
- **② 量**: cache_read 絶対量（= context 引きずり）。1/10 価格でも量が膨大なら$は嵩む
- **③ 回収**: **再利用倍率 = cache_read ÷ cache_creation**。書込は入力の 2.0倍・
  読みは 0.1倍（1h TTL — CONTRACT §5）なので、**損益分岐は 1.11**
  （価格構造から導出できる絶対閾値。未満 = 書くだけ書いて捨てている）。
  家: Cost Opt 診断 §6（TTL跨ぎ再開回数 §7 と併読。2026-07-13 実測: 13.2 / 11回/7d）

**高率の罠（率が高くても損）**:

| ケース | 実態 | 値 → 対処 |
|---|---|---|
| 率高 × cache_read 量が巨大 | 引きずり | context推移・固定費（Today 05）→ O1/O2 |
| 率高 × 往復が多い | 細切れ依頼で巨大 prefix を回数分再読 | 完遂数 × 固定費 → O9 |

**低率の原因分解（なぜ途切れたか）**:

| 原因 | 観測パターン | 対処 |
|---|---|---|
| 新セッション / clear 直後 | 朝一・分母小（正常 — Today は分母ガードでグレー） | 不要 |
| 設定変更（CLAUDE.md/MCP/モデル切替） | cacheRead比率の谷が変更時刻と一致（Context） | O13 |
| TTL 失効（1h超放置）後の再開 | 谷が長い空白の直後 | O3 |
| 短命セッションの乱発 | 再利用倍率が低い（書き逃げ） | セッション統合 |
| 生 input 大（巨大貼り付け・web ペイロード） | input 比率の上昇（トークン内訳） | O11（web 分は仕様・許容） |

キャッシュ改善に固有の操作は無い — すべて既存の O1/O2/O3/O9/O11/O13 に
ルーティングされる（有効率は症状指標）。

## 代表シナリオ（巡回からの動線）

- 背景コスト比率が赤 → 構成top6 で主犯確認 → away_summary なら O12 を施策候補へ
  （その場では開きっぱなしセッションを閉じる）
- context推移で 150K 破線超 × まだ続ける → O1（早め compact）。一区切りなら O2。
  途切れて右端まで空白 >1h のセッション → 戻らないなら畳む（O3）
- モデル×経路の本体列に意図しない高額モデル → その場で /model 切替（O7）。
  委任列が高額モデルに寄り続ける → agent への model 指定（O6）を施策候補へ
  （実例: 2026-07-13 に本体 opus $71 を当日検知）
- バーン推移のスパイク → バークリック → プロンプト一覧で主犯確認 →
  意図した重処理なら閉じる / 想定外なら止めて O5・O7 を検討
- 残り枠 <20% → O7（軽いモデル）・O4（重い探索は委任）・重い作業は明日へ
- キャッシュ有効率が黄 × 今日設定を何度も変えた → O13（変更をまとめる）を次回から
