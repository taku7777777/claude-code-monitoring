# ケースブック — 画面と数値で辿る判断サンプル

docs/USECASE.md の4ユースケースについて、「どの画面のどの値を見て、どう判断し、
何をするか」を具体的な数値で辿る。Case 1〜3 の数値は **2026-07-11〜12 に実際に
観測された値**、Case 4 はタスク=workspace 運用開始後を想定した仮想値。

## Case 1（UC1）: 「昨日の高額プロンプト」を明細まで降りて理解する

**起点**: 夕方の振り返り。Cost Optimization（7d）の「コストドライバ prompt別 top15」。

| Step | 画面 / パネル | 見る値（実測） | 判断 |
|---|---|---|---|
| 1 | Cost Opt → コストドライバ top15 | 1位 `c9486f14…` **$7.97** | 同画面の p50/p90/p95(期間) = **$0.135 / $0.454 / $0.724** と比較。p95 の **11倍** → 外れ値。理由を説明できるべき件 |
| 2 | prompt_id をクリック → **Prompt明細** | 本文「サブエージェントを使っているか否か…」/ モデル×ソース: **away_summary $4.76 / repl_main_thread $3.19 / agent(haiku) $0.02** | 意外な事実: 高額の主因は自分の依頼（$3.19）ではなく**背景機能 away_summary が6割**。「自分のプロンプトが悪い」と誤診しかけたのを明細が止めた |
| 3 | 同画面 → トークン種別内訳 | cache_read **94%**、input 0.4% | 本体 $3.19 の内実は「長寿命セッション終盤で毎ターン巨大な cache_read を引きずる」構造。プロンプト文面の問題ではない |
| 4 | `scripts/show-session.sh 111ddd46…` | 実際のやりとり（調査→実装→検証の3往復） | 作業内容に対して $3.19 は相応と判断 |

**アクション**: ① away_summary を施策候補リストへ（→ Case 3 に接続）。② 学び:
「200K 超の context を引きずったセッションでは1往復 $0.5〜1 かかる。重い調査は
新セッション or 委任で」という**単価感覚**を獲得。

**養われる感覚の例**（この日の実測から）: 軽い質問1往復 ≈ $0.1〜0.2 /
context 満載セッションの1往復 ≈ $0.5〜1 / haiku 委任1体 ≈ $0.02 /
fable 委任1体 ≈ $2〜3（$/起動 stat = **$2.26**）。

## Case 2（UC2）: 水曜13時、ペース比が赤 — 今日の残りをどう使うか

**起点**: 毎日のクイックチェック。Usage 末尾の「日次ペーシング」行。
（同曜日サンプルが3週分溜まった後の想定。数値は本日実測の消費規模を踏襲）

| Step | 画面 / パネル | 見る値（例） | 判断 |
|---|---|---|---|
| 1 | 本日の実効トークン消費 | **12.4M**（13時時点、黄 15M / 赤 20M 設定） | 絶対値はまだ上限内 |
| 2 | 過去同曜日の同時刻消費（3週平均） | **6.9M** | — |
| 3 | ペース比（本日/同曜日平均） | **1.8**（赤 >1.5） | いつもの水曜の倍近いペース |
| 4 | 消費カーブ（5分ビン） | 10:00-11:30 に集中スパイク、過去平均カーブは 14時以降に約 **+5M** 増える形 | このままいつも通り午後を過ごすと着地 ≈ 12.4M + 5M×1.8 ≈ **21M で上限超過** |
| 5 | 原因の帰属: Usage ソース別 / ワークスペース別コスト推移 | スパイクは特定 workspace の agent:* が大半 | 午前の fan-out が原因。午後の通常作業が犯人ではない |

**アクション**（分岐）:
- ペース比 >1.5: 午後は高額モデルの新規 fan-out を止める / 委任は `model: sonnet` 指定 /
  優先度の低い重タスクは翌日に回す。
- 逆にペース比 <0.5 の日: 「余らせ気味」。溜めていた重いリファクタや調査系を回して
  日次枠を使い切る（USECASE の「あまりがないように」の実践）。

## Case 3（UC3）: 週次レビュー — 健康診断の赤から施策1本を決めて検証まで

**起点**: 週次15分レビュー。Usage 先頭の「健康診断」行（数値は 7/12 未明の実測）。

| Step | 画面 / パネル | 見る値（実測） | 判断 |
|---|---|---|---|
| 1 | 健康診断行 | キャッシュ有効率 **87.4%**(緑) / 背景コスト比率 **28%**(黄) / unlabeled比率 3%(緑) / **委任の高額モデル比率 ≈100%(赤)** / 委任率 60%(緑) | 赤が1つ、黄が1つ。赤から着手 |
| 2 | Cost Opt → agent種別×モデル | general-purpose × **fable-5 $24.65** / sonnet $0.22 / haiku $0.02。$/起動 **$2.26**、呼び出し **11回** | 委任のほぼ全額が最高額モデル。内容（探索系 fan-out）に対して過剰スペックの疑い |
| 3 | 概況 → CPSO | **$2.98**（前日 $1.94 → 上昇） | 成果数は増えている（18）ので「効率の劣化」。原因は Step2 と整合 |
| 4 | 黄の背景コスト28%の内訳: ソース別コスト | **away_summary $11.9 / prompt_suggestion $3.99**（1h窓） | 第2候補としてリスト。同時には打たない |
| 5 | RICE 概算 | fable委任の8割を Sonnet 化: $24.65×0.8×約80%減 ≈ **週$15前後の削減見込み**、Effort小 | 今週の施策はこれ1本に決定 |

**アクション**:
```
scripts/intervention-marker.sh --category subagent_policy \
  --desc "探索・列挙系サブエージェントを Sonnet/Haiku 既定に変更"
```
を打ってから、エージェント運用のモデル指定を変更。**他の施策（away_summary 等）は
1〜2週間打たない**（交絡防止）。

**検証（1〜2週間後）**:
1. Cost Opt「本体 vs サブエージェント コスト推移」+ マーカー縦線で構成変化を目視
2. 「日次 コスト/1M実効トークン（管理図近似）」の水準がマーカー後に下がったか
3. `python3 analysis/cost-optimization-analyzer.py` の **[f]** — I-MR 管理限界
   （X̄±2.66·MR̄）で shift 有意なら採用、**有意でなければ「効果なし」と記録して戻す**
4. 健康診断の「委任の高額モデル比率」が赤→緑に、CPSO が $2 前後へ戻ったかを確認

## Case 4（UC4）: 月次 — 同種タスクなのに CPSO が2.5倍、何が違ったか

**起点**: 月次レビュー。`analyzer --archive` の [h] / Cost Opt「タスク別サマリ」。
（タスク=workspace 運用開始後の**仮想値**。列は実装済みの実物）

| workspace | type | cost$ | CPSO$ | 委任% | 探索% | 手戻り% |
|---|---|---|---|---|---|---|
| task-20260805-checkout-refactor | refactor | 18.40 | **1.15** | 35% | 22% | 18% |
| task-20260819-cart-refactor | refactor | 41.20 | **2.94** | **4%** | **58%** | **45%** |

| Step | 画面 / 値 | 判断 |
|---|---|---|
| 1 | 同じ refactor 種別で CPSO **2.5倍**（$1.15 vs $2.94） | 仕事の難易度差か、進め方の差かを切り分ける |
| 2 | 差分3指標: 委任 35%→4% / 探索 22%→58% / 手戻り 18%→45% | 「main context で広域探索し、書いては直した」パターンの典型。難易度でなく進め方 |
| 3 | Context ダッシュボード（期間をタスク実施週に、workspace 絞り込み） → 🚩取り込み/生成比 top10 | 比 **17〜22** の prompt が上位に並ぶ（健全目安 <15）→ 読み込み過多の裏取り |
| 4 | 該当 prompt をリンクで Prompt明細へ → 本文確認 | 「リポジトリ全体を読んで方針を考えて」という粗い初手だったと判明。Read 連打・Agent 0回 |
| 5 | セッション別context量推移 | 150K 張り付きのまま3日間同一セッション → cache_read 単価が全往復に乗った |

**アクション**: 次の refactor タスクから開始テンプレを変更 — ①広域探索は Explore
エージェント（Sonnet）へ委任 ②対象ファイルを列挙してから着手 ③日を跨ぐ際は
セッションを切る。**目標値: refactor 種別の CPSO $1.5 以下**を次タスクの成功条件に設定。

**長期追跡**: `analysis/archive/tasks-*.csv` を四半期ごとに縦持ちで見て、種別ごとの
CPSO 中央値が下がっているか（=プロセス改善が効いているか）を確認する。retention
（90日）を超えた過去タスクとの比較はこの CSV が唯一のソース。

## 共通の型

どのケースも同じ5手で閉じる:

1. **異常/違和感の検知** — 健康診断・ペース比・top15・前週比のどれかが黄赤/外れ値
2. **ベースラインとの比較** — 「高い」は必ず自分の p50/p90/p95 か過去同曜日比で言う
3. **帰属** — workspace（タスク）→ モデル → ソース → prompt の順で犯人を絞る
4. **明細で因果を確認** — Prompt明細・show-session.sh で「なぜ」まで降りる
5. **施策はマーカーを打ってから1本ずつ** — 検証は管理図と analyzer [f]、有意でなければ戻す
