# コンテキスト（compact / clear 判断）

「このセッション、compact / clear した方が良いか」に答える段。
セッションの context はすべての往復で cache_read として払い直される固定費であり、
compact / clear はその固定費を下げる操作。事後診断（癖の分析）はセッション診断
（現 Context）の管轄で、ここは**いま操作するかどうか**の判断に限定する。

## 1. アクティブセッションの現在context（直近2h）【削除済み 2026-07-13】

### 表示
- 直近2hにリクエストのあったセッションの最新 context_tokens 上位5
  （workspace + session_id 先頭8桁で表示）
- 「3. セッション別context推移」の凡例（現在値の降順）と情報が重複する —
  推移側が形の情報を持つ分だけ優位のため、削除候補（取捨判断待ち）
- 黄100K / 橙150K / 赤180K（200Kコンテキスト前提の据え置き閾値。
  1Mコンテキストモデル（fable/opus[1m]）のセッションでは 600K でも余裕があり、
  色は過剰に赤く出る — 既知の限界。バーの長さは相対スケール）

### 活用
- **大きい × まだ続ける** → 早めに手動 /compact（上限到達時の auto-compact は
  直前 context が最大の状態で要約を払うため、早い方が安い）
- **大きい × 一区切り** → /clear または新セッション（要約すら不要なら clear が最安）
- **大きい × 中断予定** → キャッシュ TTL 失効で再開時に払い直しになるため、
  戻らないなら畳む
- 同じセッションが毎日ここに居座るなら癖の問題 — セッション診断で
  取り込み/生成比・compaction 履歴を見て施策候補へ

## 2. context引きずり量（/往復）【削除済み 2026-07-13】

### 表示
- 本作業（repl_main_thread）の直近リクエストが読んだ cache_read_tokens の最大
  （アクティブセッション中の最重）
- **実測（2026-07-13 突合）では context_tokens とほぼ一致する**（差 −1%程度 =
  直近入力の未キャッシュ分）。context_tokens は prefix（システムプロンプト・
  ツール定義等）込みの全量であることが「4」のテーブルと /context の合計値で
  確認された。したがって固有の判断情報を持たず、$アンカー（≒context×$1/MTok）
  としての意味のみ — **削除候補**（取捨判断待ち）
- 「次の1往復でも読み直す量」＝セッション固定費の実測値。
  $換算の目安: fable の cache_read 単価は $1/MTok（入力の1/10）なので
  650K ≒ $0.65/往復。TTL 失効後の再構築（cache_creation 1h TTL=2.0x 仮定 — CONTRACT §5）はその約20倍

### 活用
- compact / clear の損益を体感に変える: 「この固定費 × 残り往復数」が
  節約可能額の上限
- 細切れの依頼を送るほどこの固定費を回数分払う — 関連する依頼をまとめて
  1往復にする根拠もこの値
- prefix（CLAUDE.md・MCP 等）の重さの観測は cache_read との差分では**できない**
  （実証済み — 差はほぼゼロ）。prefix の観測点は「3. 推移」の
  **新セッション / clear 直後の底値**（会話が空の時点の context ≒ prefix 全量）

## 3. コンテキスト遷移

### 表示
- セッションごとの context_tokens の時系列（系列名 = workspace｜session 先頭8桁）。
  凡例は右側のテーブルで現在値の降順
- 150K（橙）/ 180K（赤）の目安破線（200Kコンテキスト前提 — 1Mモデルでは
  過剰に赤く出る既知の限界は「1」と同じ）
- 15分以上イベントが無い区間は線を繋がない。**右端までの空白 = 最終活動からの
  経過時間**（時間軸の目盛りでそのまま定量できる）
- 凡例は workspace 短縮名（8文字超は `...`）のみ。同一 workspace の複数セッションは
  凡例上同名になる（線の色で区別。個体特定は下記の遷移で行う）
- **線上の点クリック → 「このセッションに絞った Today を開く」**で、Workspace / Session
  （Today絞り込み・uid `claude-code-workspace`）へ、そのセッションの `session_id` と
  `workspace` を付与して遷移する（本日レンジ `from=now/d&to=now`）。遷移先は Today と同一
  コンテンツを当該セッションに絞った画面で、そこからさらに Context / Prompt明細へ降りられる
  （より深いセッション診断は Context の管轄）

### 活用
- compact / clear 判断を**形**で行う:
  - 段差で下がった直後 = compact/clear 済み → 今はしない
  - 急増 = 取り込み過多 → 対象限定・委任（O10/O4）を先に検討
  - 漸増しながら破線に接近 × まだ続ける → 早めに手動 /compact（O1）
- 線が途切れて右端まで空白のセッション: 空白が 1h（キャッシュ TTL）を超えて
  いたら、再開時に再構築費（読みの約20倍）を払う — 戻らないなら畳む（O3）
- 増え方が workspace の作業内容に照らして妥当かを判断する（設計調査で増えるのは
  妥当、雑作業で急増は取り込み過多のサイン）

## 4. セッション別の1往復固定費（実読量とcompact余地）【削除済み 2026-07-13】

### 表示
- 直近2hのセッションごとに、直近リクエスト（repl_main_thread）の
  context_tokens と cache_read_tokens（実読量）、その差分を並べるテーブル
- **検証の結果、実読量 ≒ context（差 −1%程度）が実証された**（2026-07-13）。
  差分列は「直近入力の未キャッシュ分」で、判断情報を持たない
- したがって「どのセッションを compact / clear すべきか」は「3. 推移」の
  形と凡例現在値で完結する — 本パネルは**削除候補**（検証記録として一時併置）

### 活用
- compact 標的の選定は「3. 推移」で行う（本パネルに固有の判断はない）
- context_tokens が prefix 込みの全量であること（= /context の合計と一致）の
  検証記録。同種の疑いが出たら再確認に使える
