# 01 — LLM コスト算定の仕組み

「プロンプトを1回送る」の裏側で何が起き、何にいくら課金されるかを説明する。
価格の SSOT は [`pricing/pricing.yaml`](../../pricing/pricing.yaml)、イベント・数式の正典は
[CONTRACT.md](../CONTRACT.md)。本書の数値は 2026-07 校正時点の snapshot。

---

## 1. 課金の基本式 — トークン量 × モデル別単価

課金対象は文字数でも往復回数でもなく **トークン**。1リクエストのコストは
4種類のトークンにそれぞれの単価を掛けた合計になる:

```
cost = input×単価(in) + cache_read×単価(in)×0.1
     + cache_creation×単価(in)×(1.25 or 2.0)   ← TTL 5分 / 1h で異なる（§3）
     + output×単価(out)
```

| トークン種別 | 意味 | 単価（input 比） |
|---|---|---|
| `input` | キャッシュに乗らず、**書き込み対象にもならなかった新規入力** | 1.0x |
| `cache_read` | キャッシュから読めた入力。会話履歴の再送は通常ここに落ちる | **0.1x** |
| `cache_creation` | 今回新たにキャッシュへ**書き込んだ**入力。書込プレミアム付き | 1.25x（5分TTL）/ **2.0x（1h TTL）** |
| `output` | モデルが生成した出力（**thinking を含む**） | **5.0x**（全モデルで out/in 価格比 = 5） |

モデル別単価（$/1M tokens、2026-07 校正値。最新は pricing.yaml）:

| モデル | input | output | 備考 |
|---|---|---|---|
| fable-5 / mythos-5 | 10 | 50 | 最高額。新世代トークナイザ |
| opus 4.5〜4.8 | 5 | 25 | 4.7+ は新世代トークナイザ |
| sonnet 4.5〜5 | 3 | 15 | sonnet-5 は新世代トークナイザ |
| haiku 4.5 | 1.5 | 7.5 | 最安 |

さらに最終コストへの乗算係数がある: **Batch API = 0.5x / fast mode = 2.0x / US geo 指定 = 1.1x**。
新世代トークナイザ（fable-5 / mythos-5 / opus-4.7+ / sonnet-5）は**同一テキストで約 +30%
トークン化**するため、名目単価が同じでも実効単価は上がる。

> 直感との差分: 「output は input の5倍」だが、実際の支配項はたいてい input 系
> （とくに cache_read）。長い会話では毎往復 10万トークン級の履歴を再送するのに対し、
> 出力は数千トークンだからである（§2）。

## 2. 1プロンプト = 複数 API リクエスト（ステートレス + エージェントループ）

API は**ステートレス**で、サーバーは会話を覚えていない。毎リクエスト、
`system プロンプト + ツール定義 + 全会話履歴 + 新しい入力` を丸ごと送り直す。
さらに Claude Code はエージェントとして動くため、あなたの1プロンプトは
**ツール往復のたびに1リクエスト**を消費する:

```
あなたの1プロンプト（= prompt_id 1つ）
 ├─ req 1: [tools+system+履歴+プロンプト]            → 応答（tool_use: Read）
 ├─ req 2: [↑全部 + Read の結果]                     → 応答（tool_use: Edit）
 ├─ req 3: [↑全部 + Edit の結果]                     → 応答（tool_use: Bash）
 └─ req N: [↑全部 + …]                               → 最終応答（Stop）
```

帰結が2つある:

1. **毎リクエストが「それまでの全部」を再送する**。キャッシュが効いていれば大半は
   cache_read（0.1x）で済むが、コストの土台は常に**引きずっている context 量**。
   同じ「1往復」でも、新セッションなら $0.1 未満、context 満載のセッション終盤なら
   $0.5〜1 かかる（環境依存の実測目安 — [ONBOARDING E1](../ONBOARDING.md)）。
2. **ツール往復（turn）が多いほどリクエスト数が増え**、そのたびに context 全量の再送
   （＋ツール結果の新規取り込み）を払う。取り込んだツール結果は以降ずっと履歴に残り、
   次のプロンプトのコストにも乗り続ける。

本リポジトリではこの1リクエストが `api_request` イベント1件に対応し、
prompt_id / session_id で束ねて集計する（[CONTRACT §3.1](../CONTRACT.md)）。

## 3. プロンプトキャッシュ — 効く場合

- **prefix 完全一致**で効く。リクエスト先頭（tools → system → 履歴）からバイト単位で
  前回と一致する範囲がキャッシュから読まれる（0.1x）。一致が途切れた位置から後ろは、
  キャッシュ書込対象の範囲（cache breakpoint まで）が cache_creation、対象外が
  input として課金される。Claude Code は会話末尾まで書込対象にするため、実測では
  新規分はほぼ cache_creation に現れる。
  （breakpoint の配置や最小キャッシュ長などの厳密な条件は簡略化している。
  正確な仕様は公式の prompt caching ドキュメントを参照）
- **TTL はアクセスのたびに延長**される。会話を続けている限りキャッシュは温かい。
- TTL は 2種類: **5分（書込 1.25x）/ 1時間（書込 2.0x）**。実測では Claude Code の
  キャッシュ書込は **1h TTL（2.0x）で課金**されている（pricing.yaml の校正結果。
  telemetry は TTL 内訳を持たないため 2.0x の単一仮定で再計算する — 混在時は数%過大）。

健全な連続作業では、入力の 85%以上が cache_read になる
（＝ダッシュボードの「キャッシュ有効率」の健全域）。

## 4. キャッシュが切れる/効かない場合

prefix 一致が壊れると、それまで cache_read（0.1x）で読めていた範囲を
cache_creation または input として処理し直す。**キャッシュへ再書込される部分の単価が
最大 20倍**（0.1x → 2.0x）に化けるのが「キャッシュ切れ」の実体
（output や hit が残った部分は別なので、リクエスト総額が20倍になるわけではない）。

| 途切れさせる行動 | 何が起きるか |
|---|---|
| **放置（TTL 超過）** | キャッシュ失効。再開時に context 全量を書込単価で**再構築**（§5） |
| **/clear・新セッション** | 履歴を捨てる＝キャッシュも捨てる。次の会話はゼロから積み直し（意図的なら正しい判断） |
| **モデル切替** | キャッシュはモデル別。切替直後の1往復は全量書き直し |
| **ツール・設定の変更**（MCP 追加、settings 変更等） | prefix 先頭側（tools/system）が変わり、**履歴全体**が無効化 |
| **compaction（/compact 含む）** | 履歴を要約で書き換えるため無効化。ただし context 自体が縮むので以降の往復は安くなる（先行投資） |

## 5. 放置のコスト — 再構築費

応答完了後に放置して TTL（実測 1h）を超えてから再開すると、次のリクエストで
context 全量が cache_read → cache_creation に化ける:

```
150K tokens の context を放置後に再開した場合の1回分の差額
  opus:  150K × $5/M  × (2.0 − 0.1) ≈ $1.4
  fable: 150K × $10/M × (2.0 − 0.1) ≈ $2.9
```

避けるべきは「**TTL 失効後に重い旧セッションへ戻る**」こと: 続きが要らないなら
旧セッションは再開せず新規で始める（再構築費ゼロ）、同じ context がどうしても要るなら
再構築費を織り込んで再開する — これが「離れるならセッションを切る」の実体。放置中はさらに
away_summary 等の**背景機能**（query_source が repl_main_thread / agent:* 以外。発火条件は
非公式・推測 — [1-references/query-source.md](../1-references/query-source.md)）のコストが
発生しうる（[02 §7](02-optimization-levers.md)）。

## 6. 中断・エラー — 課金はされるが計上されない

送信後の中断（Esc）はクライアント側でストリームを打ち切るだけで、**サーバー側では
入力処理と中断時点までの出力生成が課金済み**。しかも `api_request` イベントは
リクエスト完了時のみ発火するため、**中断時に進行中だった1リクエスト分**は telemetry に
トークン・コストが残らない（エラー終了も同様。1プロンプトが複数リクエストに跨る場合、
中断前に完了済みのリクエストは通常どおり計上される）。

つまり本リポジトリの計上コストは**実請求の下限**である。規模の proxy は
Cost Optimization「計測ヘルス: 未計上コスト」（中断疑い件数 × 平均リクエスト単価）、
真値は月次の請求突合のみ（[CONTRACT §3.1 の警告](../CONTRACT.md) / RUNBOOK §5）。

## 7. thinking と effort

- **thinking（思考）トークンは output として課金**される（5.0x 単価）。表示されない
  思考も課金・実行時間の両方に乗る。
- **effort**（`low`/`medium`/`high`/`xhigh`/`max`）が直接制御するのは思考量。
  **一般に**高いほど思考トークン・行動量（ツール往復）が増え、出力コストと実行時間が
  伸びる傾向がある（影響の大きさはタスク・モデル依存の経験則で、単調な保証はない）。
  effort は `api_request` の structured metadata に記録される（CONTRACT §3.1）。

## 8. サブエージェント

サブエージェント（Explore / general-purpose 等）は**独立した context とキャッシュ系譜**を
持つ別のリクエスト列（query_source = `agent:*`）。親セッションは「起動指示＋結果の
要約」しか払わず、探索で読んだ大量ファイルは親の履歴に残らない。
代わりにサブエージェント自身のトークンは**委任先モデルの単価**で丸ごとかかる
（実測: haiku 委任1体 ≈ $0.02、fable 委任1体 ≈ $2〜3 — [CASEBOOK Case 1](../CASEBOOK.md)）。

## 9. 本リポジトリでのコストの扱い（L2 への接続）

| 値 | 役割 |
|---|---|
| `cost_recalc` | **表示の基準値**。pricing.yaml の単価 × 実トークンを collector で再計算（ADR 0006） |
| `cost_usd` | SDK 推定。乖離監視用（±10%黄 / ±25%赤） |
| 実請求 | ground truth。月次で突合し pricing.yaml を校正（RUNBOOK §5） |
| `effective_tokens` | 価格ウェイト正規化の作業量: `input×1.0 + cache_read×0.1 + cache_creation×1.25 + output×5.0`。比率指標の連続性のため実課金 2.0x 判明後もウェイト 1.25 を据え置き（CONTRACT §5） |
| `context_tokens` | `cache_read + cache_creation`。履歴（prefix）の重さを見る**運用指標**であり、キャッシュ外の新規入力 `input` を含まないため API の総入力そのものではない |
