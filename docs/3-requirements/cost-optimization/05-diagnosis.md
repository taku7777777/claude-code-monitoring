# 診断（寄与度・帰属）

削減候補は必ずここから選ぶ。読み順: prompt top15 → model → source → work_type。

## 1. コストドライバ prompt別 top15

### 表示
- prompt 単位コストの上位15件（コスト降順）。各行に**占有率＝総額に対するシェア**を
  バー＋%で併記（LogQL の `on() group_left()` で各prompt ÷ 全prompt総額を算出）
- 行リンクで Prompt明細ダッシュボードへ遷移できる

### 活用
- パレートの vital few 特定。施策候補は常にここが起点
- **占有率で集中度を判断する**:
  - 上位数件が大きなシェア（集中）→ その少数を直せば効く。個別潰し（Prompt明細）が有効
  - 上位でも各数%で横並び（分散）→ 個別潰しは効きにくい。横断施策
    （モデル運用ルール・context 運用の癖）で全体を下げる方が効く
  - ※「上位2〜3件で過半」は集中しているデータの話。分散していることもある
    （占有率で実際を確認する。実測で top が数%横並びのケースあり）
- 1件の $ が高いかどうかはベースライン（Prompt コストパーセンタイル §4 の p95）と比較して言う

## 2. work_type別コスト

### 表示
- タスク種別（feature/incident/design/refactor/chore…）ごとの期間コストシェア

### 活用
- 種別への配分の妥当性判断（incident に月いくら等）
- 想定配分と乖離したらタスクの引き受け方・優先度を見直す

## 3. model別コスト

### 表示
- モデル別の期間コストシェア

### 活用
- モデル使い分けルール（「Fable/Opus は設計・レビューだけ、実装は Sonnet」等）の
  根拠づくりと監査
- ルール逸脱（雑タスクに高額モデル）を見つけたら model_switch 施策の候補に

## 4. query_source別コスト

### 表示
- 発生経路（どの処理系統が API を呼んだか）別のコスト実額（降順）。
  各 query_source の意味・確度は [query_source リファレンス](../../1-references/query-source.md)
- 大きく2種類に分かれる:
  - **前景（自分が指示した）**: `repl_main_thread`（本体対話）/ `agent:*`（サブエージェント委任）
  - **背景（裏で自動発生）**: `away_summary`（離席中の要約）/ `prompt_suggestion`（入力補完）/
    `compact`（圧縮）/ `generate_session_title`（タイトル生成）/ `web_search_tool` / `web_fetch_apply` 等

### 活用
- **読み方＝前景と背景を切り分ける**。`repl_main_thread` が大半なのは正常（実作業）。
  問題は**背景コストの絶対額**——「自分が直接頼んでいないのに掛かっている額」
- **背景の各行に『それは払う価値があるか』を問う**。価値に見合わなければ Claude Code の
  設定で機能オフ・頻度調整 → 実作業に影響ゼロで削れる「タダで拾える施策」
  （例: 補完をほぼ使わないのに `prompt_suggestion` が高い、離席要約 `away_summary` が高い等）
- `agent:*` は意図した委任なのでここでは評価しない（サブエージェント §6 で委任の妥当性を見る）
- 健康診断「背景コスト比率」が黄の時の内訳確認にも使う

## 5. 実効トークン vs 生トークン

### 表示
- 重み付き処理量（実効トークン）と生トークン合計の2線（1hビン）

### 活用
- 乖離が大きい（生 > 実効）＝キャッシュに守られている証拠（cache_read が実効では 0.1x で効くため）
- 2線が接近してきたらキャッシュ効率劣化のサイン →
  cacheRead比率（Context ダッシュボード）で谷の時刻を特定する
- 注: 実効は output を 5x で重み付けするため、**output 急増でも 2線は接近する**
  （キャッシュ劣化と紛らわしい）。接近を見たら必ず cacheRead比率で真因を確認する

## 6. キャッシュ再利用倍率（read÷creation）

### 表示
- cache_read ÷ cache_creation（期間内）
- 書込は入力の 2.0倍・読みは 0.1倍（1h TTL — [CONTRACT §5](../../CONTRACT.md)）
  のため、損益分岐は **1.11**（価格構造から導出できる絶対閾値 — 自己基準でない
  数少ない例）。<1.11 赤 / 黄緑の境界 3 は初期案（実測で較正。2026-07-13 実測 13.2）

### 活用
- キャッシュ経済性3軸（構成=有効率 / 量=実効トークン / **回収=本パネル**）の回収担当
- <1.11 = 書くだけ書いて捨てている。原因は短命セッションの乱発か TTL 失効の多発
  （隣の TTL跨ぎ回数と併読）→ セッション統合・畳む習慣（O2/O3）
- 有効率が高くても本比率が低い期間は「作っては捨て」を疑う
  （判断基準の全体は today/judge-and-change-scenario.md「キャッシュ有効率の判断基準」）

## 7. TTL跨ぎ再開回数（放置>1h）

### 表示
- wait_time_observed の duration_seconds > 3600（現キャッシュ TTL）の件数（期間内）
- 失効後の再開は context 再構築（読みの約20倍）を払う。650K セッションなら ≒$13/回

### 活用
- 「セッションを畳む」（O3）の頻度観察と施策の効果検証（マーカー前後で本回数が
  減ったか）
- 回数 × その時の context 規模 ≒ 失効税の概算。多い週は away_summary 側
  （query_source別）も同時に膨らむ（放置の副作用が両方に出る）
