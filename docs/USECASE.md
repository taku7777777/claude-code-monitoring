## プロンプトと実行にかかるコストの感覚を掴む

### 目的

- どんな前提で、どんなプロンプトや依頼を実行した場合に、結果としてどの程度のコストがかかるのか...？の肌感を養うことができる。
- 実際にかかるコストもそうですが、コストの算定基準となっているトークンなどについても、理解を深めることができる。
- 2026/07時点で、実際にコスト換算の基準となっているのは、トークンであり、トークンごとの価格帯はモデルや企業によって異なり得る。そのため実績としてどの程度のコストがかかったか...より、どの程度のトークンが必要となったか...を理解できることで、より汎用的なコスト感覚を養うことができると想定しています。

### 必要なこと

- 実際に、どんなプロンプトを送信したかを振り替えることができる。数日経過すると確実に忘れてしまい、感覚を養うことは難しい。少なくとも同じ日に振り返りつつ、前提や状況、実行したプロンプトを解像度高く思い出すことができる。
- 入力トークン、出力トークン、実際にかかったコスト...について詳細に理解することができる
- 特定のプロンプト、セッションに限定・特化した、コンテキストや使ったツール、スキル、サブエージェント...など、コストに関連し得る要素の情報を、把握してコストへの影響の目算を立てることができる。
- IDなどを指定することで、ローカルに溜まっているCladueCodeとのやりとりの履歴から、実際にどんなやりとりをしたか...をサルベージすることができる

## 日次の利用量が適切か...を把握して最適化できる

### 目的

- 現状、1日に利用できるコスト帯がある程度決められており、このコスト帯を超過しないようにしつつ、あまりあまりがないように効果的に運用できるようにしたい
- そのために、1日の中で、過剰にトークンを消費し過ぎていないか...などタスクの属性や難易度ごとに適切にコストを最適化できているか...という観点ではなく、利用戦略として1日ごとにある程度安定的に戦略的にコストをコントロールできているか？...という観点での政略

### 必要なこと

- 1日ごとの利用量
- 過去の同じ曜日の利用実績から、時間ごとのトークン利用量の変遷の傾向、参考値と比較して現時点の実績を把握することができ、参考値と比較して使い過ぎでいるのか？あまり使えていないのか？...を把握することができる。


## 日次/週次で使い方を振り返り、コスト感が妥当か？を振り返る

### 目的

- 1日を通して、ミクロではなくマス的な観点で振り返る
- 自身の使い方の傾向を、一般的な傾向と、過去の自身の使い方と比較して傾向を理解しつつ、乖離がある場合はその乖離が妥当か否かを確認する

### 必要なこと

- 一般的に使われる観点で、 その日1日のマクロ的な数値や実績を参照することができる
- 一般的な推奨値と比較して、自身の実績を比較することができ、乖離している値を理解することができる
- 過去の自身の平均値と比較して、自身の実績を比較することができ、乖離している値を理解することができる

## タスクごとにコストが妥当か否かを振り返る

### 目的

- 日付ベースではなく、タスクごとにかかったコストや使い方が適切かを把握し、必要な改善を実行することができる。
- タスクによって、開発関連やインシデント、改善系、設計がガッツリ必要なタスクごとにかかるコストやトークン、傾向も変わりえます。

### 必要なこと

- 実際にタスクごとに、過去分全て含めて、かかったコストやトークン、傾向を参照することができる
- 同じタスク種別などでグルーピングして、比較したり、同じタスクの中でも設計があるもの、ないもの、設計部分にかかったコスト、実装、テストでかかったコスト...一度作成してからレビューやFBをして治す必要があった部分などを把握して、タスク単位での一連のプロセス・取り組みを振り返ることができる

# 実現計画（前提: タスク = workspace）

運用前提: **タスクごとにディレクトリを作成し、タスク = workspace として扱う**。
workspace は index label としてほぼ全パネル・全イベントに付与されるため、UC4 の
「タスク別分解」は追加計測なしで成立する。タスクディレクトリから `task-outcome.sh` を
打てばタスク別 CPSO も自然に成立する。

## Phase 0 — 前提を計測面で成立させる土台（最優先）

| # | 内容 | 理由 |
|---|---|---|
| P0-1 | `scripts/init-task-workspace.sh <dir> [--type <種別>]`: タスクdir作成時に `.claude/settings.json`（workspace=dir名, work_type=種別）を自動生成 | settings が無い新規タスクdirは `~/github` のフォールバックに吸われ **workspace=github に化けて不可視**になる。タスク作成フローに組み込んで漏れを構造的に防ぐ |
| P0-2 | `~/github/.claude/settings.json` の workspace を `github` → `unlabeled` に改名（または削除） | ラベル漏れが「github」という一見正当な名前に化けると検知できない。「unlabeled」なら日次チェックの workspace 一覧で即発見できる |
| P0-3 | work_type をタスク種別の taxonomy として固定（例: `feature / incident / design / refactor / chore`）し CONTRACT に記載 | UC4 の「種別グルーピング」の分解軸。settings.json 生成時に指定 |
| P0-4 | Loki retention 31d → 90d + analyzer に月次アーカイブ出力（workspace別サマリを CSV/JSONL でリポジトリに永続化） | UC4「過去分全て」/ UC2「同曜日参照」は 31d retention と矛盾する。長期比較はアーカイブ側で行う |

運用ルール（人間側）: タスク作業は必ずタスクdirから起動する。workspace 名は再利用しない
（`task-20260712-loki-retention` のように日付込み推奨）。タスク跨ぎの雑作業が
unlabeled に落ちるのは仕様（雑作業の総量として毎日見えることに価値がある）。

## Phase 1 — UC1: コスト感覚（素材は揃っており即日効く）

| # | 内容 |
|---|---|
| P1-1 | 「プロンプト明細」ダッシュボード新設: prompt_id 変数で、**user_prompt 本文**（OTEL_LOG_USER_PROMPTS=1 で収集済み）＋トークン4種＋コスト＋使用ツール＋サブエージェント利用＋turn数を1画面に |
| P1-2 | 既存の prompt別 top15/top10 テーブルに data link を付け、行クリックで P1-1 に prompt_id を引き継いで遷移 |
| P1-3 | `scripts/show-session.sh <session_id>`: ローカル `~/.claude/projects/*/<session_id>.jsonl` から実際のやりとりをサルベージ表示（telemetry の session_id とファイル名は同一） |

成功条件の例: 3週間後、新しいタスクの消費トークンを着手前に±50%で見積もれる。

## Phase 2 — UC3 / UC4: 週次レビューの強化

| # | 内容 |
|---|---|
| P2-1 | 「健康診断」行を Usage 先頭に追加: ガードレール（キャッシュ有効率>85% / 背景コスト<20% / unlabeled比率<10% / 委任モデル適正）を緑黄赤 stat で並べ、毎日3秒で乖離検知。「一般的な推奨値」はこのヒューリスティック集として定義する（外部ベンチマークは信頼できるものが存在しないため自己基準+ガードレール方式を採る） |
| P2-2 | Cost Optimization に「タスク別」セクション: workspace(=タスク)×work_type(=種別) 別の コスト / 実効トークン / CPSO / 委任率 / prompt数 サマリテーブル |
| P2-3 | analyzer に [h] タスクレポート追加: rework比率（lines_changed の file_path が複数 prompt にまたがる割合＝手戻りの代理指標）、探索/実装比（初回編集前後のコスト比）、種別別集計、アーカイブCSV出力（P0-4） |
| P2-4 | 今週 vs 先週の比較 stat（LogQL `offset 7d`）: コスト・CPSO・委任率の前週比±% |

フェーズ分解（設計/実装/テスト）の完全自動化はしない。rework比率・探索/実装比を代理指標とし、
必要なら intervention-marker（category=other, desc="phase:design" 等）の手動打刻で区切る。

## Phase 3 — UC2: 日次ペーシング（参照値が溜まってから効く）

| # | 内容 |
|---|---|
| P3-1 | 「本日の累積実効トークン曲線 vs 過去同曜日3回の平均曲線（`offset 7d/14d/21d`＋累積和変換） vs 日次上限ライン」パネル |
| P3-2 | 日次上限はダッシュボード変数で設定（コストでなく実効トークン基準。cost_usd は推定値であり、上限運用はトークンの方が頑健） |

> 注（2026-07-13 更新）: **確定仕様は [today/README](3-requirements/today/README.md) のヘッドルーム上限
> （cost_recalc 基準の 日次 $150 / 週 $600 / 月 $2000）**。cost_usd(SDK推定) ではなく cost_recalc を用いるため
> 上表 P3-2 の「cost_usd は不適」という懸念は解消済み。本 P3 は旧計画の記録として残す。

着手順: **P0 → P1 → P2 → P3**。P3 は実装しても同曜日サンプルが3つ揃う（3週間）まで
参照値が意味を持たないため最後で良い。
