# 02 — コスト最適化のレバー

[01-cost-model.md](01-cost-model.md) の仕組みのうち、利用者が動かせる変数を
「レバー」として整理する。各レバーが**なぜ効くのか（原理）/ 何をするか（打ち手）/
何と引き換えか（トレードオフ）**を対で持つ。監視の仕方は
[03-monitoring-playbook.md](03-monitoring-playbook.md)。

## レバー早見表

| # | レバー | 効く原理（01 の §） | 主に動く量 |
|---|---|---|---|
| 1 | コンテキスト量を小さく保つ | 毎リクエストが context 全量を再送（§2） | cache_read・cache_creation |
| 2 | キャッシュを途切れさせない | 切れた範囲の再書込単価が 0.1x → 2.0x（§4-5） | cache_creation（再構築費） |
| 3 | サブエージェントへ委任する | 親の履歴に探索結果を残さない（§8） | 親の context・委任先コスト |
| 4 | モデルを使い分ける | 単価比 fable 10 : opus 5 : sonnet 3 : haiku 1.5（§1） | 全トークンの単価 |
| 5 | effort を使い分ける | thinking は output 課金・行動量も制御（§7） | output・実行時間 |
| 6 | 依頼の仕方を整える | ラリー・中断・手戻りは往復数×context 再送（§2, §6） | リクエスト数・output |
| 7 | 放置と背景機能を統制する | TTL 失効＋背景機能のコスト（§5） | cache_creation・背景コスト |

## 1. コンテキスト量を小さく保つ — 最大のレバー

**原理**: 1往復の単価は文章の長さではなく**引きずっている context 量**で決まる。
一度取り込んだものは残りの全往復に乗り続けるので、序盤の大量 Read は
「そのプロンプトのコスト」ではなく「セッションの残り全部のコスト」を上げる。

**打ち手**:
- 「まず全部読んで」の粗い初手をやめ、**対象ファイルを列挙してから**着手させる
- 広域探索は Explore 等へ委任（レバー3）して親に取り込まない
- context が 150K 破線に近づいて**まだ続けるなら**早めに `/compact`（履歴の書き換え費用は
  かかるが、以降の全往復の再送量が減る先行投資）
- **話題やタスクが替わったらセッションを切る**。日を跨ぐ長寿命セッションは
  「終盤の1往復 $0.5〜1」を全往復に払い続ける形になる

**トレードオフ**: 削りすぎると Claude が前提を失い、手戻り（再説明・再読）で逆に高くつく。
「そのタスクに必要な context」は残すのが正しい。

## 2. キャッシュを途切れさせない

**原理**: prefix が壊れると、0.1x で読めていた範囲のうち再書込される部分の単価が
最大 2.0x（20倍）に化ける（01 §4-5）。

**打ち手**:
- **TTL 失効後に重い旧セッションへ戻らない**（TTL 実測 1h。150K context の放置再開で
  $1.4〜2.9 の再構築費）。続きが不要なら再開せず新規で始め、作業を続けるなら
  放置時間を TTL 内に収める
- セッション途中の**モデル切替・ツール/設定変更を避ける**。とくに tools/system が変わる
  変更（MCP 追加等）は履歴全体を無効化する — やるならセッションの切れ目で
- `/clear` は「キャッシュも context も捨てる」判断。次のタスクが前の履歴を必要と
  しないなら、むしろ積極的に切ってよい（レバー1と同じ話の裏面）

**トレードオフ**: 「キャッシュを守るために巨大 context を維持し続ける」のは本末転倒。
cache_read も 0.1x で課金され続ける。守る価値があるのは「まだ使う context」だけ。

## 3. サブエージェントへ委任する（委任先モデルまで含めて）

**原理**: 探索・列挙で読む大量テキストを親の履歴に残さない。親は結果要約だけ払う。

**打ち手**:
- 広域探索・ファイル横断調査・並列化できる独立作業は委任する
- **委任モデルを明示する**。探索・列挙系は Sonnet/Haiku で十分なことが多い。
  既定のまま高額モデル（fable ≈ $2〜3/体）で fan-out すると委任費が本体を超える
  （[CASEBOOK Case 3](../CASEBOOK.md): 委任のほぼ全額が fable で週 $25 →
  8割を Sonnet 化する施策で**週 $15 前後の削減見込み**と概算した実例）
- fan-out は**乗算**で効く。N体並列は1体の N 倍。「とりあえず並列」の前に体数と
  モデルを見積もる

**トレードオフ**: 単ファイルの読解や逐次作業まで委任すると、起動オーバーヘッド＋
結果の再説明でかえって高い。「親 context を守る価値がある量か」で判断する。

## 4. モデルを使い分ける

**原理**: 単価は fable 10 : opus 5 : sonnet 3 : haiku 1.5（input, $/1M）。全トークンに効く
ので、モデル選択はそのセッション/委任の全コストの倍率になる。新世代トークナイザ
（fable-5 / opus-4.7+ / sonnet-5）は同一テキスト約 +30% トークン化のため、
実効差は名目単価差よりさらに開く。

**打ち手**:
- 難タスク（設計・長時間自律作業）に高capabilityモデル、定型・探索・要約は下位モデル
- 「安いモデル×ラリー増で総額は逆に高い」パターンに注意（ONBOARDING E6）。
  能力不足による手戻り・往復増はモデル単価差を食い潰す
- セッション**途中**の切替はキャッシュ無効化を伴う（レバー2）。切替はセッション境界で

## 5. effort を使い分ける

**原理**: effort は思考トークン（output 課金）と行動量（ツール呼び出し回数 → リクエスト数）
の両方を動かすため、**一般にコストと実行時間は同方向に動く**（影響の大きさは
タスク・モデル依存の経験則。効果は前後比較で確認する — [03 §3](03-monitoring-playbook.md)）。

**打ち手**:
- 定型作業・軽い質問・サブエージェントは low/medium、難タスクは high/xhigh
- 「時間がかかりすぎるが結果は正しい」タスクは effort を1段下げる余地のサイン
- 高 effort で長時間回すときは、途中中断（§6）や放置（§7）と組み合わさると
  無駄が増幅される点に注意

**トレードオフ**: 下げすぎは浅い推論による手戻りを生む。effort は
`api_request` の structured metadata で事後確認できる。

## 6. 依頼の仕方を整える

**原理**: 曖昧な依頼 → 探索やラリーが増える → リクエスト数 × context 再送が増える。
中断時に進行中だった分はサーバー側課金済み＋telemetry 未計上で、
成果につながらない課金になりやすい（01 §6）。

**打ち手**:
- **最初の1回で完全指定する**（目的・対象・制約・完了条件）。逐次追加のラリーは
  1往復ごとに context 全量再送を払う
- 依頼の背景（何のためか）を添える。意図が伝わると無関係な探索が減る
- **送ってから止める（Esc）を減らす**。送信前に依頼を固める。中断時に進行中だった分は
  課金されるうえダッシュボードにも乗らない（未計上コスト）。暴走を止める中断は正しい判断
  なので、減らすべきは「依頼を固めずに送って止める」パターン
- 手戻り（作らせてから大幅に直す）が多いタスク種別は、着手前の設計・レビューを挟む

## 7. 放置と背景機能を統制する

**原理**: 放置は (a) TTL 失効の再構築費を生み、(b) away_summary 等の背景機能コスト
（query_source が repl_main_thread / agent:* 以外。発火条件は非公式・推測 —
[query-source.md](../1-references/query-source.md)）も放置中に発生しうる。背景機能は
「自分の依頼でないのにコストを食う」ため、気づかないうちに膨らむ。

**打ち手**:
- 応答が返ったら次の指示か終了かを決める。**待たせている時間**（放置率）を減らす
- 背景比率が恒常的に高い（≥20%）場合、原因機能を特定して設定で無効化・抑制を検討
  （実測例: 高額プロンプトの6割が away_summary — [CASEBOOK Case 1](../CASEBOOK.md)）

## レバー同士の関係

- レバー1（context）とレバー2（キャッシュ）は同じコイン: 「小さく保つ」×「切らさない」。
  矛盾したら**小さく保つ方を優先**（cache_read も課金され続けるため）。
- レバー3（委任）はレバー1の実現手段だが、レバー4（委任モデル）を誤ると逆効果。
- レバー6（依頼の仕方）は全レバーの上流。依頼が良ければ探索も往復も減る。
