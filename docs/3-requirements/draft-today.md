## 位置づけ

5ページ・3層構成（常時 / 定期巡回=日次・週次 / 事象駆動×2）の「常時」層を担う新設ページ。
本ドラフトでの頁名の対応: Usage / Cost Opt は現行のまま、
**セッション診断 = 現 Context のリネーム予定**、Prompt明細 は現行のまま。

答える問いは1つだけ:

**「今、余裕があるか。ペースを変えるべきか。異常は出ていないか」**

既存ページとの本質的な違いは、振り返り（過去の説明）ではなく
**進行中の資源配分の意思決定**（pull型）を支えること。1日のコスト枠は
使い切っても翌日に持ち越せず、余らせても返ってこない「消える資源」なので、
配分判断は事後でなく日中に行う必要がある（[USECASE.md](../USECASE.md) UC2 が原点）。

## 確定事項（2026-07-13）

1. **上限は3階層のコスト基準**: 日次 **$150**（毎日 00:00 起点）/ 週次 **$600**
   （月曜 00:00 起点）/ 月次 **$2,000**（毎月1日 00:00 起点）。
   - **UC2 の旧決定「上限運用はトークン基準」を上書きする**。旧決定の前提は
     「cost_usd は推定値であり信用できない」だったが、cost_recalc（単価表×実トークン、
     請求突合で校正 — ADR 0006）への切替でこの前提は解消済み。正式化時に
     USECASE.md P3-2 の記述も是正する
   - 拘束力の階層に注意: $150×7=$1,050 > 週$600、$600×4.3=$2,580 > 月$2,000。
     つまり**日次$150 はバースト許容枠であり、定常の実効ガバナは月次**
     （平均 ≈$66/日、≈$500/週）。日中判断は日次枠で行い、週次・月次の消化管理は
     週次レビュー（Cost Opt バーンレート節に予算ラインを正式導入）が主担当。
     Today には週残り$・月残り$を無色で併記する（色判定しない — 期間が長いほど
     「残り%」は自然減するため静的閾値が意味を持たない）
2. **表示は$基準に統一**: 残り枠・カーブ・ペース比・バーンとも$。バーンは
   **$/h を主表示、実効トークン/h を併記**（上限が$になった以上、主従もこちらが一貫）
3. **家の移設**: ガードレール行・ペーシング行は Today へ移し Usage から削除（単一の家）。
   朝の儀式は「Today で3秒 → Usage で振り返り」の2段
4. **同曜日サンプル不足時のフォールバックは持たない**（初期運用時のみの問題。
   参考値なし表示のまま）
5. **自動リフレッシュは 10〜30秒**（初期値 30s。stat は instant query 化して軽くする。
   ローカルスタックのため許容想定だが、負荷が問題になったら間隔を戻す）
6. **push の通知経路に macOS 通知は使わない**（経路はメール等を別件で検討。
   対象は A3 を第一候補とする方針は維持）
7. **閾値は決め打ちで開始**: A1・A6・最低分母ガードの N は初期値を決め打ちし、
   運用しながら「パネル＋本カタログの同時更新」の既存規約で変更する
   （較正のための事前採取はしない）
8. **着地予測 stat は置かない**: 日末着地の目算は累積カーブ（時間軸x）の目視外挿で行う

## 実現したいこと（ユースケース）

### UC-T1. 着手前のヘッドルーム確認（プリフライト）

**場面**: 重い処理（大規模リファクタ、レビューの fan-out、長時間 agent、調査系の
ultracode 相当）を投げる直前。

**目的**: 「今日この枠でやるか / 明日に回すか / 軽い構成（モデル・委任先）に変えて
やるか」を、感覚でなく残り枠を見て決める。

**必要なこと**:
- 残り枠（日次上限 $150 − 本日消費$。上限比%を主表示・$併記）が1つの数字で分かる
- ペース比（本日$ / 過去同曜日の同時刻$平均）で「いつもの自分」との比較ができる。
  ただしペース比は平常比であって上限比ではない。**上限に対して日末どこに着地するかの
  目算は累積カーブの目視外挿（UC-T3）で行う**（確定事項 8 — 専用 stat は置かない）
- 直近の実勢バーン（直近1hの $/h。実効トークン/h 併記）が分かる —
  「いま何かが走っていて速く減っている最中か」の判断材料
- 週・月の残り$が視界にある（週$600・月$2,000 — 日次が緑でも定常ガバナは月次。
  確定事項 1）

### UC-T2. 定点チラ見（5秒の巡回）

**場面**: 日中に数回、作業の合間。判断はしない。

**目的**: 「枠内で、異常なし」を5秒で確認して閉じる。黄・赤のときだけ立ち止まる。

**巡回プロトコル**(判断の手順を固定する。重篤度と即時性を単調に揃える):

1. **黄・赤が無ければ閉じる**（グレー = 最低分母ガード発動中は「判定保留」で
   正常扱い — 色に置く条件 3）。ここまで5秒
2. **赤** → 即、[異常カタログ](#異常カタログガードレール仕様の正)の該当行の
   「降り先」へ降りて対処する。**原因が意図した実行（承認済みの重処理・大規模
   fan-out 等）なら、想定内として何もせず閉じる（正常終了の分岐。これが無いと
   黄赤の心理的重みが摩耗する）**
3. **黄** → 次の作業の区切りで降り先を確認する（30秒）。その場で直らないもの
   （行動の癖・ワークフロー起因）は施策候補として週次レビュー（Cost Opt）へ送る

**必要なこと**:
- 無スクロール・無操作で全体が視界に入る
- 色（緑黄赤）だけで判読が完了する。精密値を読ませない。
  **文脈判断（「今は昼休みだから古くて当然」「朝だから分母が小さくて当然」等）を
  要求する色を置かない**
- 毎回同じ位置に同じ数字がある（空間記憶で読む。レイアウトを変えない）
- ガードレールの各 stat が異常カタログの1行と1:1で対応し、黄赤時の降り先が
  リンクとして埋まっている（「この色は何を意味し、次にどこを見るか」を暗記させない）

### UC-T3. ペース調整の判断（日中のステアリング）

**場面**: 昼過ぎ・夕方の区切り。

**目的**: 「使いすぎ → 残りは軽めの作業に切り替える」「余っている →
後回しにしていた重い作業を今日中に消化する」の両方向の判断。
枠は余らせても返ってこないため、**使い切る方向の判断も対等に扱う**
（超過検知だけなら本ページは不要で、アラートで足りてしまう）。

**必要なこと**:
- 本日の累積消費$カーブ（時間軸x） vs 過去同曜日の平常$カーブ vs
  **日次上限ライン（$150）** が1枚で重なって見える
- 「このままのペースなら日末どこに着地するか」が目視で外挿できる（確定事項 8）

### UC-T4. 実行直後のコスト感覚フィードバック（最重要）

**場面**: 依頼を1本走らせ終えた直後。とくに「これは高そう/安く済むはず」と
何かしらの予想を持っていたとき。

**目的**: 「この依頼ならこれくらい」という肌感は、**予想→実測→乖離の理由を見る**の
反復でしか育たない。この反復を、専用の操作ゼロ〜1クリックの低摩擦で1日に何度も
回せるようにする（UC1「±50%で見積もれる」の日中実装）。

**FBサイクルの設計**（3段階・浅い順）:

1. **受動反復（毎回・0クリック・3秒）**: Today に「直近プロンプト5件（時刻 /
   コスト / 実効トークン / 本文先頭）」のミニテーブルを常設する。チラ見のたびに
   「さっきの1本 = $0.4」が勝手に目に入る。**予想を書き留めなくても、直後に実測が
   毎回目に入る構造そのものが訓練になる**（このために専用の行動を要求しない）。
   直近行の時刻は**計測鮮度の確認を兼ねる**（いま送った依頼が載っていなければ
   計測が壊れている — 異常カタログ A8 の補助）
2. **能動確認（気になったとき・1クリック・30秒）**: 乖離が気になった行をクリック →
   Prompt明細に prompt_id 付きで遷移。「なぜその値段か」を
   本体/委任/背景の別 → トークン4種 → モデル×経路 → ツール・turn数 の順で特定する
   （高かった理由の典型: 委任の fan-out / 背景機能の便乗 / キャッシュミス /
   turn数過多。誤診防止の実例: $20.2 の主因が away_summary だったケース）
3. **深掘り（稀・数分）**: やりとりの中身まで戻るときは
   `scripts/show-session.sh <session_id>` で全文をサルベージ

**必要なこと**:
- 直近プロンプトのミニテーブルが Today の視界内にある（0クリック目が成立する）
- 行クリックで Prompt明細へ prompt_id 引き継ぎ遷移（既存の行リンク方式を流用）
- 直近1hバーン stat（実行前後の消費差がヘッドルーム行でも読める）

### UC-T5. 静かな逸脱の当日検知

**場面**: 逸脱は起きた瞬間ではなく、数時間単位でじわじわ効いてくる。

**目的**: 従来は翌朝の Usage まで最長1日放置していた逸脱を、当日中に拾って
その日のうちに直す。

**何をどう確認するかは下の異常カタログに全量を定義する**。ガードレール stat は
カタログの「色」行の実装であり、判断手順は UC-T2 の巡回プロトコルに一本化する
（T5 で独自の判断はしない。T2=巡回の体験、T5=検知対象の網羅、という分担）。

## 異常カタログ（ガードレール仕様の正）

このシステムで実際に起こり得る逸脱の全量。**検知は層に振り分ける**:

- **色**: Today のガードレール stat（pull）
- **push**: Grafana alerting（別件）。ページを見ていない時に起きるものだけ
- **週次・月次**: 変化が遅く当日判断に繋がらないもの。Today には置かない
- **表示**: 無色の常設情報（色判定はしないが視界に置く）
- **運用**: パネルでなくプロセスで防ぐ

**色に置く条件**（1つでも満たさなければ色に置かない）:
1. 巡回時点で証跡が残って見える値であること（瞬間条件は巡回とすれ違う —
   無人バーンの教訓）
2. 文脈判断なしに緑黄赤が読めること（偽陽性が定常発生する色は黄慣れで
   プロトコル全体を殺す）
3. 比率系は**最低分母ガード**を併設すること（now/d は毎朝分母が小さく、
   1日の最初のプロンプトは cache_creation 主体でキャッシュ有効率が必ず低い等、
   朝は構造的に偽陽性になる。本日消費が閾値 N 未満の間は無色・グレー表示にする。
   N は決め打ちで開始し運用で調整 — 確定事項 7。実装方式の検証は実装時の検証事項）

閾値はすべて自己基準（決め打ちの初期値から開始し、運用で較正 — 確定事項 7。
変更時はパネルと本カタログを同時更新）。

**2026-07-13 運用後の取捨（実ページへの反映済み）**: 色ガードレールは
A2（背景コスト比率）と A5（キャッシュ有効率）の2枚に縮小した。
A6 は workspace別サマリの autoCmp 列、A7 は同テーブルの unlabeled 行、
A9 は累積カーブの $150 線＋本日コストで目視代替。
**A8 の色（collector死活）は削除し、鮮度（ミニテーブル直近行の時刻）が唯一の検知**
（計測停止の検知力は下がる — 問題が起きたら色の復活を再検討）。

**push（alerting）の設計方針**: pull の網羅（色）と push の厳選を分ける。push は
「ページを見ていない時間帯に発生し、当日中に知る価値がある」A3（無人バーン）を第一候補、
A1・A9赤を第二候補とし、それ以外は push しない（通知疲れで全通知が無視されるのを防ぐ）。
通知経路に macOS 通知は使わない（メール等を別件で検討 — 確定事項 6）。

## 設計制約（4条件+チラ見特有）

1. **半画面以内・無スクロール**: 目標 約18グリッド単位（540px）以下。
   タブ・サブモニタに常駐させられる密度
2. **無操作**: 変数選択・フィルタ・凡例クリックを前提にしない。開いた瞬間が完成形
   （例外: ミニテーブルの行クリック遷移は「1クリック目」として許容 — UC-T4）
3. **固定時間意味論**: now/d（本日）+ 直近1h をパネル側で固定。
   ユーザーのレンジ変更に反応しない。週残り$は now/w（月曜起点）、
   月残り$は now/M（1日起点）をパネル側で固定
4. **空間安定性**: パネルの位置・順序を変えない。増設は末尾のみ（連番規約と同型）
5. **色で読む**: 色を持つ stat は異常カタログの行と1:1対応する。
   **カタログ行を持たない stat は無色（数値表示のみ）とする** — 本日$・ペース比・
   週残り$・月残り$は無色。文脈判断を要求する色は置かない（カタログの「色に置く条件」）
6. **自動リフレッシュ 10〜30秒**（初期値 30s — 確定事項 5）。stat は instant query 化
