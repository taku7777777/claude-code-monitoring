# ベースライン（分布）

「普通」= このセクションの p50/p90/p95。「高い/安い」は感覚や平均でなく、この3値との比較で言う。
単位を混ぜないこと: **prompt単位 = 依頼1回の値段**（依頼の仕方の問題）/
**APIリクエスト単位 = セッションの重さの値段**（context 運用の問題）。対処が違う。

## 1. API Request コスト分布

### 表示
- APIリクエスト1件あたりコストの分位点を、**x軸=分位点（p50 / p90 / p95）× workspace別
  色分け縦棒**の1枚で表示。各分位点の群に **「全体」基準バー（凡例先頭）＋各 workspace** が
  並び、色→workspace は下部凡例で引く
- 1リクエストのコスト ≒ その瞬間に持ち歩いている context の重さ＋出力長
- 色は workspace ごとに固定（3群で同色）。値は全 $__range を集計した断面値（時系列ではない）。
  コスト基準は cost_recalc（欠損時 cost_usd にフォールバック）
- 時系列散布図 → workspace別グループ化横棒 → 本構成、と改訂（2026-07-12）。
  workspace名をx軸に置くと視認性が崩れるため、x軸は分位点（3群のみ）に固定し、
  workspace は色（凡例）で識別する形にした

### 活用
- 各群で **「全体」バーと各 workspace バーの高さを比較**し、上に出る workspace ＝ 上振れ、
  下 ＝ 下振れ を即断する。全体より高い workspace がそのセクションの要注意先
- p50 群で全体より高い ＝ その workspace が慢性的に重い context を引きずっている
  （セッション運用の施策候補）
- **p95 群だけ突出**する workspace ＝ 裾が重い（TTL 払い直し・compaction 直後などの
  イベント系リクエストの混入）。p50（山）の問題か p95（裾）の問題かを群間で切り分ける
- 全 workspace が全体バー付近に揃うなら、コスト差はモデル選択の問題と切り分ける
- **低活動 workspace の高分位点は小標本で不安定**（数リクエストだと p95 ≒ その窓の最大値）。
  確定基準は §2 の全体分位点を使い、この群は乖離の当たり付けに使う

## 2. API Request コストパーセンタイル

### 表示
- 期間全体の APIリクエスト単位コストの3分位点。「普通」の基準値そのもの
- 「1」の workspace 別分位点を、全 workspace 横断（`by ()`）でまとめた全体分位点。
  集計単位・期間は同じでグルーピングだけが違う（分位点は時間方向に単純合算では
  合成できないため、両者は別クエリで算出している）

### 活用
- 週次レビューでこの3値をメモし、自分の基準値として持つ（RUNBOOK §2.2）
- 外れ値判定の足切りに使う: 気になる APIリクエスト1件の $ が p95 以内なら
  通常範囲として流し、p95 超だけを診断セクションで個別に追う
- 分布の山（≒p50）自体が動いたら「使い方の変化」。個別案件でなく
  概況・効果検証セクションの話として扱う

## 3. Prompt コスト分布

### 表示
- プロンプト1回あたりコスト（prompt_id 単位の期間合計）の度数分布を、
  **workspace 別に積み上げ色分け**したヒストグラム。「依頼の仕方」の値段
- 色→workspace は下部凡例で引く。各ビンの色構成で「その価格帯のプロンプトが
  どの workspace のものか」がわかる
- 正確な分位点の数値は右の §4（Prompt コストパーセンタイル）で読む
  （cost_usd 基準の analyzer [c] とは基準が異なる。§4 参照）

### 活用
- 診断 top15 や Prompt明細で見た「プロンプト1件の $」はこの分布
  （または analyzer [c] の p95）と比べる。p95 以内なら通常範囲として流す
- 山の位置（≒p50）が動いた＝使い方自体の変化（重大シグナル）→
  概況・効果検証セクションで扱う
- 右裾だけ伸びた＝外れ値管理の問題 → top15 → Prompt明細で個別に潰す
- **右裾（外れ値）の色で原因の当たりをつける**: 特定 workspace 1色に集中していれば
  その workspace 固有の問題（そのタスクの進め方）、複数色に散っていれば横断的な
  使い方の問題（モデル選択・context 運用の癖）として切り分ける

## 4. Prompt コストパーセンタイル

### 表示
- prompt_id 単位の期間合計コストの p50/p90/p95。§2（api_request 単位）の prompt 版で、
  「上段=API単位・下段=prompt単位」の対の下段にあたる
- per-prompt 合計を出してから Grafana の transform（reduce）で分位点を算出する。
  LogQL は prompt 単位の分位点集約に非対応だが、per-prompt 値を1列に畳んで
  Grafana 側で percentile reducer を掛けることで**ダッシュボード上でライブ算出**できる
- コスト基準は cost_recalc（欠損時 cost_usd）。§3 ヒストグラムの山(≒p50)・右裾(p95)の数値裏付け

### 活用
- 「依頼1回の普通の値段」の基準値。診断や Prompt明細で見た prompt 1件の $ を
  この p95 と比べ、p95 以内なら通常範囲として流す
- **§2（API単位）と対で読む**: API単位 p95 は普通なのに prompt単位 p95 だけ高い＝
  1依頼あたりのラリー（往復）が多いタイプの重さ。API単位も高い＝1リクエストが重い
- analyzer [c] は同じ prompt単位分位点を **cost_usd 基準**で出す。本パネルは
  **cost_recalc 基準**なので、単価表と SDK 推定の差（概況§6の乖離）分だけ数値がずれる。
  ダッシュボード内の整合を優先するなら本パネル、SDK 推定との比較は analyzer [c] を使う
